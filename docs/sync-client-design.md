# Reflector — the client side (KMP + Room + Ktor)

The specification of the client library: the mechanism, the storage schema and the contract it
requires from the server. The companion document:
[the server module specification](sync-server-design.md).

---

## 1. Decisions taken

| Question | Decision |
|---|---|
| Offline writes | Full offline-first |
| Conflicts | Optimistic version, the server refuses stale writes, the client resolves |
| Change format | A full snapshot of the entity (state-based) |
| Atomicity | A group of operations is applied atomically, groups are independent |
| Detecting local mutations | An explicit API call inside the transaction |
| Storing bodies | Lazy materialisation through the adapter, no base snapshot is kept |
| Identifiers | Generated by the client; UUIDv7 is recommended for entities, not required |
| Conflict resolution | A callback into the application |
| Write semantics on the server | Patch-merge by the keys present |
| Data volume | The whole collection; subscription filtering is deliberately not designed |
| Real time | WS `invalidate` + HTTP pull |
| Encryption | None, the server sees plaintext |
| Links between collections | None, collections are independent |
| Scope | One active scope, logout wipes the data |
| Platform triggers | A port into the application; the library only knows a timer |
| Unpushed queue at logout | An explicit choice by the application: `signOut(discardPending)` |
| Conflicts nobody answers | Reported as a derived `NEEDS_ATTENTION` phase, never expired |
| Local schema drift | An optional fingerprint per collection, and `requestResync()` by hand |
| An oversized group | Detected locally before the envelope goes out; the application fixes it |
| Diagnostics | Two ports into the application: numbers to aggregate, and a log to read |

## 2. The model

```
scope (usually a userId, may be shared)
└── collection (ledger)          — the unit of consistency, of the cursor and of the worker
    └── entity type (wallet, transaction)
        └── entity (UUID, v7 recommended)
```

A collection is the boundary of everything: its own cursor, its own worker, its own
bootstrap, its own push queue. Ordering between collections is not guaranteed and is not
needed, because there are no references between them.

The library does not own business rows. It stores only sync metadata and reaches into the
application through a `CollectionAdapter` for serialisation and application of changes.

## 3. The storage schema

The library's tables live in the **same `@Database`** as the application's tables —
otherwise applying incoming changes and advancing the cursor could not be done in one
transaction, and after a crash the cursor would diverge from the data.

```sql
sync_collection(
  scope_id TEXT, collection_id TEXT,   -- PK
  cursor TEXT NULL,                    -- opaque server token
  epoch TEXT NULL,                     -- which incarnation of the collection that cursor is in
  phase TEXT,                          -- NEW | BOOTSTRAPPING | LIVE | RESYNC_REQUIRED
                                       -- NEEDS_ATTENTION is never stored here: it is derived
                                       -- from the open conflict count when state is published
  generation INTEGER NOT NULL,         -- ++ on every bootstrap (mark & sweep)
  bootstrap_page TEXT NULL,
  last_pull_at INTEGER,                -- every pull that reached the end of the log, empty
                                       -- or not, and every finished bootstrap
  last_push_at INTEGER,                -- only a push the server applied; a client with an
                                       -- empty queue never pushes, so this can lag far behind
  schema_fingerprint TEXT NULL,        -- the application's declared shape of its own tables
  last_error TEXT NULL, failure_count INTEGER
);

sync_inbox_batch(
  scope_id TEXT, collection_id TEXT, seq TEXT,   -- PK
  cursor TEXT NOT NULL,                -- the position to store once this batch has been applied
  …
);

sync_record(
  scope_id TEXT, collection_id TEXT, entity_type TEXT, entity_id BLOB(16), -- PK
  server_version TEXT NULL,     -- opaque version; NULL = the server does not know the record
  local_rev  INTEGER NOT NULL DEFAULT 0,
  pushing_rev INTEGER NOT NULL DEFAULT 0,
  acked_rev  INTEGER NOT NULL DEFAULT 0,
  intent TEXT NULL,             -- UPSERT | DELETE (the latest local intent)
  group_id BLOB(16) NULL,       -- the push group the dirty record belongs to
  conflict_id BLOB(16) NULL,
  seen_gen INTEGER NOT NULL
);
CREATE INDEX ix_sync_record__scope_id__collection_id__group_id
  ON sync_record(scope_id, collection_id, group_id);

sync_group(
  group_id BLOB(16) PRIMARY KEY,
  scope_id TEXT, collection_id TEXT,
  ord INTEGER,                  -- monotonic local order; the push is strictly FIFO
  state TEXT,                   -- PENDING | IN_FLIGHT | CONFLICTED | FAILED
  attempts INTEGER, next_retry_at INTEGER,
  dependency_merges INTEGER NOT NULL DEFAULT 0,  -- merges after rejected: DEPENDENCY
  last_error TEXT NULL
);

sync_conflict(
  conflict_id BLOB(16) PRIMARY KEY,
  scope_id, collection_id, entity_type, entity_id,
  origin TEXT,                  -- PULL | PUSH
  local_payload TEXT NULL,      -- materialised at the moment of detection
  server_payload TEXT NULL,     -- NULL = the server deleted the record
  server_version TEXT,
  detected_at INTEGER
);

sync_inbox_batch(
  scope_id, collection_id, seq TEXT,   -- PK
  received_ord INTEGER NOT NULL,       -- arrival order: seq is opaque and sorts
                                       -- incorrectly as text ("10" < "9")
  origin_client_id BLOB(16) NULL, state TEXT
);
sync_inbox_op(scope_id, collection_id, seq TEXT, ordinal INTEGER,  -- PK
              entity_type, entity_id BLOB(16), op TEXT, version TEXT, payload TEXT NULL);

sync_meta(
  scope_id TEXT PRIMARY KEY,
  client_id BLOB(16) NOT NULL,         -- the installation identifier echo suppression rests on
  created_at INTEGER NOT NULL
);
```

The index over `(scope_id, collection_id, group_id)` is what the queue reads with: the push takes a
group and then its records. A partial index on `local_rev > acked_rev` would serve the dirty scan
more directly, but `@Index` has no predicate, so it would have to be written by hand in a migration
— worth doing if a profiler asks for it, not before.

`entity_id` is stored as `BLOB(16)` rather than as a textual UUID: on a collection of
hundreds of thousands of rows the difference in table size is threefold.

**Invariants**

- `dirty(R) := R.local_rev > R.acked_rev`
- `dirty(R) ⟺ R.group_id IS NOT NULL` (or `R.conflict_id IS NOT NULL`)
- A collection's cursor advances only together with the application of a batch, in one
  transaction.
- The client clock takes part in no decision. Ordering and versions are the server's alone.

## 4. Push groups and coalescing

Lazy materialisation means that a push sends the entity's **current** state, not the state
it had at the moment of the edit. Hence the consequence: if an entity was edited in local
transaction T1 and then in T2, its state at the moment of T1 can no longer be reconstructed —
which means T1 and T2 cannot be sent as two independent groups.

The solution is **merging groups by entity intersection**:

```
mutate { markUpserted(...) ... }:
  1. let S be the set of entities touched by this transaction
  2. G := the set of PENDING groups that already own at least one entity from S
     (IN_FLIGHT groups do not take part: they have already been sent)
  3. merge every group in G into one and add S to it; ord = min(ord of the groups in G)
  4. if G is empty — create a new group with ord = next()
```

The groups end up being the connected components over shared entities and by construction do
not intersect. Atomicity is preserved: if two changes were ever in one local transaction,
they will reach the server together.

The degradation is honest: a "hot" entity that is edited constantly pulls the group into one
large one — that is, in the limit the behaviour degenerates into "the whole envelope
atomically". That is exactly the price that cannot be avoided under state-based semantics.

**Ordering.** The push is strictly FIFO by `ord`, with one group in flight per collection.
Groups do not intersect by entity, but they may depend on each other logically (a wallet
created in group N, a transaction against it in N+1), and without reference information the
library cannot see such dependencies. FIFO closes the question at the cost of a stuck group
blocking the ones behind it.

The queue therefore reads its **head** — the smallest `ord`, whatever state it is in — and decides
there whether it can be sent. Selecting the oldest *pending* group instead would pay the price of
the ordering and give none of it back, sending the group behind the stuck one. The decision has
four outcomes: `PENDING` past its backoff goes out; `IN_FLIGHT` is a push whose answer never
arrived and goes out again under the same identifier; `CONFLICTED` and `FAILED` stop the whole
collection until the application resolves or corrects them; a backoff not yet expired is the head's
to serve, and nothing overtakes it meanwhile.

A group with nothing left in it is discarded rather than waited for. That is what the application
reacting looks like from here: correcting a refused entity moves it into a later group, and what it
leaves behind is a shell whose records are gone. Without that step, refusing to look past the head
would block the collection permanently.

**Rows that existed before synchronisation: `adopt`.** Data the application held before there was
an owner to synchronise it for — a device used without an account whose owner now signs in — has
no metadata row, so nothing would ever send it. Marking all of it inside one `mutate` would be
correct and useless: one block is one group, a group is never split, and a group holding a whole
table is refused locally as too large and then blocks the queue behind it.

`adopt(entityType, ids)` is the other shape. Those rows were never changed together, so nothing
ties them, and they are queued as consecutive groups of at most `maxOperationsPerGroup`, in the
order given — the order matters for the same reason FIFO does above, so a caller passes the rows
others refer to first. Every group is created in one transaction: all or nothing, so a process
that dies part-way leaves nothing to reconcile. Only rows with no metadata row are taken; a row the
library already tracks keeps its state, which makes the call idempotent and is also why it can
never pull an existing group into these and make it too large.

The limit is the server's, read by the first cycle. `adopt` waits for that answer rather than
guessing a size or asking on its own: guessing too high blocks the queue, guessing too low costs a
round trip per group, and a second request would race the cycle's. Until the limit is known nothing
is queued.

**The "edited while in flight" race** is closed by revisions: when the envelope is assembled
`pushing_rev := local_rev`; on ack `acked_rev := pushing_rev`. If `local_rev` moved ahead
while the envelope was in flight, the record stays dirty and after the ack joins a new group.

What matters is that until the ack it does **not** change its `group_id`: the envelope is
already on the wire, and a retry with the same `groupId` must reproduce exactly the same set
of operations. If an edit immediately moved the record into a new group, the retry would send
an envelope poorer than the original — and the atomicity of the local transaction, the very
reason the group exists, would be split across two server batches. For the same reason a new
mutation does not join a group in the `CONFLICTED` or `FAILED` state: those are waiting for a
decision, and mixing a fresh edit into them is not allowed.

## 5. Push

```
1. tx: take the oldest group with state=PENDING and next_retry_at <= now,
       state := IN_FLIGHT, and for its records pushing_rev := local_rev
2. for every record: payload = adapter.snapshot(entityType, id)
       snapshot() == null with intent=UPSERT ⇒ treated as DELETE
3. POST /v1/sync/{scope}/{collection}/push
4. tx: parse the response (see below)
```

```jsonc
// request
{
  "clientId": "…",
  "groups": [{
    "groupId": "…",                       // the idempotency key
    "ops": [
      {"entity":"wallet","id":"…","op":"upsert","baseVersion":"41","data":{…}},
      {"entity":"transaction","id":"…","op":"delete","baseVersion":"7"}
    ]
  }]
}

// response
{
  "results": [
    {"groupId":"…","status":"applied",
     "versions":[{"entity":"wallet","id":"…","version":"42"}]},
    {"groupId":"…","status":"conflict",
     "conflicts":[{"entity":"…","id":"…","serverVersion":"50","data":{…}}]},
    {"groupId":"…","status":"rejected",
     "error":{"code":"VALIDATION","entity":"…","id":"…","message":"…"}}
  ],
  "latestSeq": "1187"
}
```

- `applied` → `server_version := newVersion`, `acked_rev := pushing_rev`, the group is
  deleted; records whose `local_rev > acked_rev` join a new group.
- `conflict` → the group becomes `CONFLICTED`, the conflicting records receive a
  `conflict_id`, and the group's non-conflicting records stay dirty and wait for the
  resolution (the group is atomic).
- `rejected` → the group in its current form was not accepted; what happens next depends on
  the code.
  - `DEPENDENCY` — the server refused the group because of a dependency on another one (a
    transaction refers to a wallet the server has not seen yet). The group is merged with the
    collection's next `PENDING` group and goes out again, and `dependency_merges` is
    incremented. A ceiling is mandatory: after `maxDependencyMerges` the group is moved to
    `FAILED`, otherwise client and server could bounce merges forever. If there is no next
    group, the group stays `PENDING` with a backoff — the dependency may be closed by somebody
    else's change.
  - any other code (`VALIDATION`, `UNKNOWN_ENTITY_TYPE`, `TOO_LARGE`) → the group becomes
    `FAILED` and `adapter.onRejected(...)` is called. This is a path distinct from a conflict:
    retrying without changing the data is pointless, and would otherwise produce a poison
    message that blocks the queue forever.

**The idempotency key is reused only when the same envelope is repeated.** If the response
did not arrive — a network failure, a timeout, a `5xx` — the group goes out again with the
same `groupId`, and it is exactly this case the server keeps the result for. But as soon as
the group's content changes — a merge after `DEPENDENCY`, a reassembly after a conflict was
resolved — it must receive a **new** `groupId`. The server keeps the result under
`(client_id, group_id)` for any outcome, refusal included, and a repeat with the old key
would return the stored answer instead of looking at the new content. A group with a new
identifier takes the ordinal of the oldest of the merged ones — otherwise the merge would
push changes ahead of the queue.

The plain retry is the third case, and it is decided by `pushing_rev`. An entity edited again
while its group waits for its backoff joins that same group — it has to, since the two states can
no longer be separated — so the group now holds a record whose `local_rev` has moved past the
revision the envelope was assembled at. A group in that condition that has already been sent (an
attempt behind it, or left `IN_FLIGHT`) is rebuilt under a new identifier before it goes out, in
the same way as after a merge: same ordinal, same dependency-merge count, attempts from zero
because a backoff describes how one particular envelope was received.

If the server did apply the abandoned envelope, the new one arrives with base versions it has moved
past and comes back as a conflict — which is the whole difference: visible, and offered to the
application, rather than acknowledged as confirmed by a server that never saw it.

**A local record survives a confirmed deletion.** After an ack for a `delete` the
`sync_record` row remains, with its `server_version` set — a local tombstone. It must not be
removed: an entity created anew with the same id would go out with `baseVersion = null`,
while the server remembers the deleted record and would return a conflict out of nowhere.
Tombstones are cleaned up by the sweep at the next bootstrap, where they are absent from the
snapshot anyway.

**A collection's cursor does not move in response to a push**, even when the server returned
`latestSeq`. Our own changes arrive through an ordinary pull and are applied idempotently;
trying to cut the corner leads to jumping over other people's changes that landed in between.

`latestSeq` is used only as a "there is something to fetch" hint — it wakes the pull worker.

## 6. Pull

```
GET /v1/sync/{scope}/{collection}/changes?cursor=&limit=500
{
  "batches": [
    {"seq":"1184","originClientId":"…|null",
     "ops":[{"entity":"wallet","id":"…","op":"upsert","version":"42","data":{…}}]}
  ],
  "nextCursor":"1184", "hasMore": true
}
```

```
tx1: write the page into the inbox
for every batch in order:
  tx2: adapter.applyRemote(ops') + update sync_record + cursor := batch.seq
repeat while hasMore
```

Pages are cut by the server **only at batch boundaries** — a cursor never points inside one.
The two-phase design (inbox → apply) gives two things: a crash while applying does not
require downloading from the network again, and one server transaction equals exactly one
local transaction.

**The rule for applying a single operation** (`R` is the local record, `op` the incoming one):

```
R.server_version == op.version           → no-op (already known)
R is clean                               → applyRemote(op); R.server_version = op.version
R is dirty && op.originClientId == me    → R.server_version = op.version  (our own echo,
                                            business tables are left alone)
R is dirty && a foreign origin           → conflict: op is NOT applied to the business
                                            tables, the payload and the version are written
                                            to sync_conflict in the same transaction
```

The last branch matters: a conflict is detected **on the pull**, not only when a push is
refused. Naively "applying" overwrites the user's edit; naively "skipping" loses the change
forever, because the cursor moves on regardless. Recording the conflict in the same
transaction makes it durable.

**An unknown operation code.** The log carries two operations, `upsert` and `delete`. If a batch
contains an `op` the client does not know — a code from a newer server version — the batch is not
applied and the collection is moved to `RESYNC_REQUIRED`. Skipping is unacceptable here for the same
reason as above: the cursor would move on and the change would be lost forever.

That rule is what makes adding an operation code a breaking protocol change: every client that meets
one resynchronises, so it cannot be rolled out gradually and needs a version negotiation first. See
§8 of the server specification for why nothing is queued to be added.

## 7. Conflicts

Both paths (`PULL` and `PUSH`) converge into one queue, and an entity has at most one open
conflict in it. The schema says so — a record holds a single `conflict_id` — and both paths have
to honour it, because the same disagreement is reachable from either: a push refused by the
server, and then the change that refused it arriving through the log over the same still-dirty
record. The second detection updates the open conflict instead of adding to it, bringing both
states and, above all, the server version up to date; the origin and the moment of detection stay
as they were. Inserting a second row would leave the first with nothing pointing at it — counted
in `conflictCount` for the life of the collection, and impossible to answer, since a decision on
it would be applied to a record that has moved past the version it was detected against.

Resolution is a synchronous callback into the application:

```kotlin
sealed class Resolution {
    data object KeepLocal : Resolution()       // re-push ours on top of the server version
    data object TakeServer : Resolution()      // apply the server's, drop the local change
    data class Merged(val data: JsonObject) : Resolution()
}
```

The adapter may decline to decide: `CollectionAdapter.resolve` returns `Resolution?`, and
`null` means "the user is needed". Such a conflict stays open and is published through
`CollectionHandle.conflicts`, from where the application resolves it by calling
`resolve(conflictId, …)`. Without this fork we would have to either force the adapter to
decide synchronously at the moment of detection — that is, to guess on the user's behalf — or
always park the conflict in a queue even where the policy is obvious.

The merge is two-sided (mine vs the server's), with no common ancestor — a deliberate
decision, so that the library does not store a copy of the data. An application that needs
the ancestor can keep it itself.

Applying a resolution, in one transaction:

- `KeepLocal` → `server_version := conflict.serverVersion`, `local_rev++`, the group returns
  to `PENDING`.
- `TakeServer` → `applyRemote(serverPayload)`, `server_version := serverVersion`,
  `acked_rev := local_rev`, the record leaves the group.
- `Merged(data)` → `applyRemote(data)` + `local_rev++` + `server_version := serverVersion`,
  the group goes to `PENDING`.

If `server_payload == null` (the server deleted the record we were editing) this is a
delete/update conflict, and `KeepLocal` means recreating it with the same id.

**Conflicts nobody answers are reported, not expired.** A conflict blocks its group and the queue
is FIFO, so a collection whose conflicts pile up has stopped synchronising while still calling
itself `LIVE` — a lie of omission, and the one thing the library can fix without deciding anything
on the user's behalf. Once the number of open conflicts reaches `conflictThreshold`
(`ConflictThreshold.Default` is 20), the published phase becomes `NEEDS_ATTENTION` instead of
`LIVE`, and it goes back on its own as the conflicts are resolved.

The phase is **derived when the state is published and never written to `sync_collection`**. The
stored phase decides which worker may run, and the answer to a pile of conflicts is that they all
keep running — a pull still applies other people's changes, and a push still drains the groups that
hold no conflicting entity. A stored phase would also have to be recomputed by whichever writer
happened to come next, and would be wrong until one did. Only `LIVE` is replaced: a collection that
is bootstrapping or has lost its cursor is already saying something more urgent.

Nothing expires a conflict and nothing resolves one on a timer. An age-based policy would keep the
queue moving by throwing away the user's work after N days, which is precisely what an
offline-first library exists not to do; the threshold buys the same visibility and decides
nothing.

## 8. Bootstrap and resync

Triggers: `phase = NEW`, `410 cursorTooOld`, `409 collectionReset`, the WS message `resync`.

```
generation++
GET /v1/sync/{scope}/{collection}/snapshot?page=&limit=
  → {"cursor":"1100",
     "items":[{"entity":"wallet","id":"…","version":"42","data":{…}}],
     "nextPage":"…","hasMore":true}
every applied record: seen_gen := generation
on completion: sweep — remove everything with seen_gen < generation (through the adapter),
               cursor := cursor (the one the server returned on the first page),
               phase := LIVE
```

A snapshot item must carry a version: without it `server_version` would stay empty after the
bootstrap, and the very first push would go out with `baseVersion = null`, which the server
reads as "I am creating a new entity" and answers with a conflict out of nowhere. Deleted
entities do not appear in a snapshot — the sweep removes them by `seen_gen`.

The snapshot is "dirty": the server fixes `cursor0` before it starts serving and does not
hold repeatable read across all the pages. Repeats are possible, omissions are not — and
under snapshot semantics a repeat is idempotent.

The sweep does not touch dirty records: they survive a resync and go out with a push. The one
exception is a reset, below, where there is nothing for them to survive into.

### The collection was replaced: `409`

A purge on the server does not age a cursor out, it invalidates it. The collection begins again
under a new identity, and everything this device holds — the cursor, the versions, the queue, the
open conflicts — describes a log that no longer exists.

The client cannot work that out for itself, so the server names the incarnation and the client
carries it:

```
sync_collection.epoch := the epoch of every answer (changes, snapshot, push)
POST …/push   {"clientId":…, "epoch":"<the one stored>", "groups":[…]}
  → 409  when that incarnation is gone; nothing of the request was applied
GET  …/changes?cursor=…      → 409 when the cursor names an incarnation that is gone
```

**The push carries it, and that is the point.** The worker pushes before it pulls, so a client that
only learned about the purge from a read would already have re-created, entity by entity, the data
the purge removed — and the server could not tell those writes from ordinary new ones. The epoch
travels with the push so that the refusal arrives *before* anything is written.

On `409` the collection is emptied and rebuilt:

```
groups, conflicts, inbox for this collection := deleted
every record := clean (local_rev := acked_rev, server_version := NULL)
cursor := NULL, epoch := NULL, bootstrap_page := NULL, phase := RESYNC_REQUIRED
then the ordinary bootstrap, whose sweep deletes every application row the new snapshot omits
```

**Unsent local changes are discarded, and this is the only place the library does that on its
own.** A
conflict is a disagreement between two versions of an entity; after a purge there is no other
version to disagree with, and keeping the edits would mean deciding, against an explicit erasure,
that this device's copy wins. The server is the source of truth and the truth is that there is
nothing. It is reported at `WARN` with the number of changes abandoned, because it is the one case
where a user can lose work that nobody on the device asked to lose. A host that cannot afford that
must stop the device from reaching the scope at all, which is what `403` is for.

The records are marked clean rather than deleted: they are what ties the library's bookkeeping to
the application's rows, and deleting them would orphan those rows. Marking them clean hands them to
the bootstrap's existing sweep, which removes both together.

**The cursor is fixed from the first page, not at the end.** `cursor0` is written into
`sync_collection.cursor` as soon as the first page arrives, and a bootstrap resumed after a
process restart continues from exactly that point. Taking a fresh `cursor0` on resume is not
possible: everything committed while the snapshot was being transferred lives only in the log
between the old and the new position, and a new cursor would silently jump over those changes.

**A dirty record in a snapshot is a conflict, not a reason to overwrite.** A bootstrap has no
`originClientId`, so the decision is made by version: if the record's `server_version` matches
the version from the snapshot, the local edit was made on top of exactly that state — there is
nothing to apply, the record stays dirty and goes out with a push. If the versions diverged,
the server has moved ahead, and this is a full conflict with `origin = PULL`: applying the
snapshot would mean throwing the user's edit away, and staying silent would mean later sending
our version on top of a state nobody ever saw.

### The user gives up: `discardLocalChanges()`

A group the server refused for good blocks the queue until the data changes. When nobody can make
the data acceptable, the way out is to throw this device's unsent work away. Only the application
can decide that, so the library offers it and never does it unprompted. `requestResync()` is not the
same thing: it keeps unsent changes, and the refused group is refused again after it.

```
in one transaction, before the call returns:
  rows of dirty records with server_version = NULL := deleted through applyRemote(Delete)
  those records and their file references         := deleted
  groups, conflicts, inbox for this collection    := deleted
  every remaining record := clean; server_version := NULL where it held a change, kept otherwise
  phase := RESYNC_REQUIRED
then the ordinary bootstrap, in the next cycle
```

**It happens when it is called, not when the worker next gets to it.** A request held in memory
until the next cycle is lost with the process, and a device without a connection may not run a
useful cycle for days — the user who pressed "discard" would go on seeing the change they threw
away. So the discard is a transaction of its own, run while the worker is held off: it cancels the
cycle running at the time and takes the lock the worker runs its cycles under. Cancelling is safe for
the same reason a process death is: everything a cycle writes is written in transactions. Waiting
instead would tie the call to whatever the cycle was doing — a long snapshot, a request waiting out a
timeout. What the call covers is exactly what was unsent when it was made; an edit made after it
returns is new work and is kept. It cannot be called from inside the adapter, which runs inside the
cycle it would be waiting for, and it says so rather than cancelling itself.

**What the server never had is removed at once.** A dirty record with no confirmed version stands
for an entity the server does not hold, so the server's state of it — absent — is known without
asking. Its row is deleted through `applyRemote` as a server deletion would be, its record and its
file references with it. A creation whose acknowledgement was lost is among them; the snapshot
brings it back, because the server does have it.

**What the server does have waits for the snapshot.** The library holds no entity bodies, so an
edit or a deletion of something the server holds can only be undone with the server's copy. Those
rows show the discarded change until the bootstrap overwrites or restores them, and the phase says
so meanwhile: the discard is complete when the collection is `LIVE` again.

**An edit made in that window is a conflict.** It is made on top of a row that still shows the
discarded change, so pushing it against the version it was confirmed at would hand the server the
discarded change after all. That is why such a record loses its `server_version` in the discard:
the snapshot then finds a dirty record whose version does not match and opens a conflict, and a push
that goes out first claims no base version and is refused for the same reason. A record that held no
change keeps its version, so an edit to an entity the discard did not touch is an ordinary edit.

## 9. Transport and triggers

```
WS /v1/sync/{scope}/events
← {"type":"invalidate","collection":"ledger","latestSeq":"1187"}
← {"type":"resync","collection":"ledger"}
← {"type":"revoked"}                        // access to the scope was revoked
```

The socket is only an alarm clock; data always travels by HTTP pull: one application path and
a trivial fallback to polling. **After every reconnect an unconditional pull is made** — an
invalidate may have been missed while the connection was down.

That is why the channel emits a stream of signals rather than a stream of events: `Connected`
and `Received(event)`. The fact of connecting is not an internal detail but the only thing
that closes the gap: notifications sent while the socket was down do not exist, and no later
message will say "you missed one". A client that reacted only to events would sit silently
stale until the next timer.

`requestResync` exists in the public API for an adjacent reason: the library cannot notice
that the application's tables have diverged from what it synchronised — a migration, a repair
after a bug, an import from the side. In such cases a bootstrap is cheaper than trusting a
cursor whose data changed underneath it. Unfinished local changes survive the resync and go
out with a push.

**The same thing can be declared instead of remembered.** `CollectionAdapter.schema` is an optional
`SchemaFingerprint` — any stable string, a version number or a hash of the DDL — stored in
`sync_collection.schema_fingerprint` and compared at the start of every cycle, before anything
reads or writes the application's rows. A value that differs from the stored one moves the
collection to `RESYNC_REQUIRED` and records the new one in the same transaction; separately, a
crash between the two would leave a collection that has forgotten it needs rebuilding.

Both paths exist because they fail differently. Calling `requestResync()` after a migration is free
and works — until somebody forgets, and then nothing happens at all: the cursor keeps moving over
tables that no longer hold what the library thinks they hold, silently, for the life of the
installation. A fingerprint cannot be forgotten, and its price is that the library holds exactly one
opinion about a schema it does not own — that a change to it means the data has to be fetched again.

Two rules keep the opt-in honest. An adapter that declares nothing keeps today's behaviour
entirely. And the first run under a declaration stores the value without rebuilding anything:
nothing is known to have changed, and sending every installation through a bootstrap on the upgrade
that introduced the declaration would be a large lie about a small fact.

The value is compared for equality and never parsed or ordered — a fingerprint that changed back to
an earlier value is still a change, because so is the migration that changed it back.

A pull is started by: application start, returning to the foreground, network recovery,
`invalidate`, a successful push, a periodic timer, a platform background task. A push is
started by a local mutation (debounced) and by network recovery.

Of that list the library sees only part from the inside: start, `invalidate`, a successful
push, a local mutation and the timer. Foreground, network recovery and the background task are
platform events, and they arrive through a port:

```kotlin
fun interface SyncTriggerSource {
    fun triggers(): Flow<SyncTrigger>       // FOREGROUND | NETWORK | PERIODIC | BACKGROUND
}
```

A port rather than an implementation inside the library, because subscribing to those events
is inseparable from the application: on Android it is its lifecycle and `WorkManager`, on iOS
notifications and `BGTaskScheduler`, and all of it drags in manifest entries, background modes
and its own initialisation order. A library that reached in there itself would demand all of
that from every application and would still be wrong for anything that is not a plain
foreground app.

Hence only two sources ship with the library: `PeriodicTriggerSource` — a timer (15 minutes by
default), the safety net under everything else in case a notification was missed and the socket
was not brought back up; and `ManualTriggerSource`, into which the application hands its own
events with one non-blocking `fire` call. A trigger sent before the engine came up is not lost
(`replay = 1`): an extra synchronisation costs nothing, while a missed one leaves the screen
stale.

The engine itself does not distinguish trigger types — it always simply synchronises. The
distinction is for diagnostics and for the application, which decides which of them it is even
able to produce.

**What a failure says is what the library knows, not less.** `SyncFailure` distinguishes the cases
by what the application can do about them, and it earns that only if it keeps what it was told.
`Network` and `Local` carry the throwable — the description of a fault in code this library does
not own is worth little without the stack that produced it — and the failures the protocol names
(refused credentials, a revoked scope) are reported as themselves. The mapping from
`SyncTransportFailure` is exhaustive rather than falling back on a catch-all, which is what had
been reporting three of them as a server error with the status code zero.

A permanent refusal reaches the application twice on purpose: through `CollectionAdapter.onRejected`,
which is a call it has to handle, and as the collection's `lastFailure`, which is what a screen
bound to that collection reads. One without the other is how a blocked queue ends up published as a
collection whose last attempt succeeded.

**Authorisation.** The token comes from a port into the application:

```kotlin
interface TokenProvider {
    suspend fun token(): String?        // null — the user is not authenticated
    suspend fun refresh(): Boolean      // true if a new token was obtained
}
```

`401` is not a transport error and not a reason for backoff. The client tries `refresh()`
once; if that did not help, the collection workers stop and the scope moves to
`ScopeState.AuthRequired`. The data and the push queue are preserved: the user signs in again and
the unfinished groups go out. `403` means access to the scope was revoked and is handled the
same way as the WS `revoked` event.

Both halves are the host's to send, and a host that sends only the first leaves the data on the
device. `403` is what makes the client wipe the scope, and the `revoked` event is what makes it
happen now rather than at whatever moment the device next asks for something — which on a device
nobody opens is not a moment that arrives. The module holds no access state and cannot send either
on the host's behalf; `samples/ledger-server` shows the pair in `ScopeRevocations`.

**`clientId`** is a stable installation identifier that echo suppression rests on. It is
generated on first access to a scope and stored in `sync_meta`. Changing it (a reinstall,
cleared data) must be followed by a bootstrap: otherwise the device's own changes would arrive
with a foreign origin and be taken for conflicts.

**The version of a UUID is a recommendation for entity identifiers and nothing at all for the
library's own.** `clientId`, `groupId` and `conflictId` are generated with `Uuid.random()` —
v4 — and that is the specification rather than a shortfall against it: none of them is an
ordered key. The queue is FIFO by `ord`, the inbox is ordered by `received_ord`, and a
conflict is looked up by identity. Entity identifiers are the application's, and there v7 does
buy something — a time-ordered key keeps the server's index inserts local — so the
recommendation stands, while nothing in the protocol reads the version nibble or would notice
a v4. A requirement that buys nothing costs a v7 constructor the standard library does not
have, in exchange for a statement no code checks.

**The server's limits** are requested once at start and cached:

```
GET /v1/sync/config
  → {"maxOperationsPerGroup":500,"maxDocumentBytes":262144,
     "maxChangesPageSize":500,"retentionDays":30}
```

Knowing them before the envelope is assembled is mandatory: a group cannot be split, so
exceeding a limit must be detected on the client and handed to the application as a
`RejectError` rather than arriving as a network refusal after a long offline stretch. The
retention window is needed for the decision to "go to bootstrap early", without waiting for a
`410`.

**What an application does about an oversized group is the application's decision, and stays
there.** The library detects the overflow, fails the group with
`onRejected(null, null, TooLarge)` and blocks the collection's queue on it; from there only the
application can move: the local transactions that produced the group committed long ago, and
splitting the group on its behalf would break the one guarantee the group exists to give. What
it can do is rewrite the data — delete or shrink the entities that no longer fit, in a fresh
`mutate`, which moves them into a later group and leaves the refused one an empty shell that
the queue discards. The library offers no strategy parameter for this, because every strategy
it could offer either breaks atomicity or asks the application to declare the group's parts
independent — a declaration nothing can check and a wrong one loses data silently.

The alternative, if a real workload ever produces such a group, is a server-side multipart
envelope: the client uploads the parts and the server commits them in one transaction when
the last one lands. It is the fallback rather than the default, and it is not built, because
it buys a stateful upload session, garbage collection of abandoned parts and a new failure
surface — all of it to serve a group that no workload has yet produced.

Retries: exponential backoff with jitter; `429`/`Retry-After` is respected; `5xx` and network
errors are transient; `4xx` other than `401`/`403`/`409`/`410` is permanent and the group goes
to `FAILED`.

**Diagnostics leave through a port, like everything else that is the application's.** Every failure
mode this library has is slow rather than loud — a queue that stops draining, conflicts nobody
answers, a collection that bootstraps every week — so "synchronisation feels stuck" is
unfalsifiable without numbers:

```kotlin
fun interface SyncMetrics {                    // implemented by the application, optional
    fun record(event: SyncMetricEvent)         // PushCompleted | PullCompleted | BootstrapCompleted
}                                              // RetryScheduled | QueueObserved
```

A port and not a `Flow`, and not a metrics dependency: the shape is the one `TokenProvider` and
`SyncTriggerSource` already have, and an application that wants a debug screen implements it over a
`MutableStateFlow` in ten lines, while one that wants a dashboard implements it over the client it
already has. The default sink discards everything.

The set of events is closed and covers what cannot be seen from outside: how the queue drains and
in what condition (`PushCompleted` carries the operation count and the outcome, so the conflict
share and the refusal rate are counts of it), how much the log delivered (`PullCompleted`), what a
bootstrap costs (`BootstrapCompleted`), how long the collection deliberately waits after a failure
(`RetryScheduled` carries the delay), and how deep the queue and the conflict list have grown
(`QueueObserved`, at the end of every cycle).

**Cursor lag is not on that list, and cannot be.** A cursor is an opaque token, so the distance
between two of them is arithmetic only the server can do — which is why the server module measures
the lag itself and the client reports the volume it applied instead. Durations are measured with
the device's clock, and, like every other use of it here, no decision reads them back.

Implementations are called on the collection's worker, never inside a transaction, and must not
throw: a metric that could fail a synchronisation which already succeeded would be worse than no
metric. A throw is swallowed, which is also why a broken sink reports nothing and says nothing.

**Numbers are not an account of what happened, so there is a second port next to them.** Metrics
answer "how is the population doing" and are built to be aggregated; they cannot answer "why did
this installation stop pushing on Tuesday", because the shape that makes them aggregable is exactly
the shape that throws away the order and the particulars. `SyncLog` is that second port:

```kotlin
fun interface SyncLog {                            // implemented by the application, optional
    fun log(record: SyncLogRecord)                 // level, event, message, context, cause
    fun isEnabled(level, source): Boolean = true   // asked before a record is built
}
```

A port and not a logging library, and here the reason is stronger than consistency with the others:
the client is multiplatform, no logging framework spans the JVM, Android and iOS, and any library
that picks one imposes it on every consumer and every target. The SDK ships `ConsoleSyncLog` for
every platform and `AndroidSyncLog` for logcat, both of which depend on nothing, and the default
sink discards.

`isEnabled` is part of the contract rather than an optimisation. It is asked before a message is
formatted or a context map is built, which is what makes it reasonable for the engine to describe
every decision it takes; and because the answer comes from the application, the levels in effect are
configured wherever that application configures every other level — externally, at runtime, and per
`SyncLogSource`, so that the push side can be made verbose while the pull side, which is far louder
on a busy collection, stays quiet.

What it reports is chosen around this library's failure modes, which are slow rather than loud. The
three that were previously invisible from outside are now stated: a queue whose head is conflicted
or refused is reported **once, when it becomes stuck** rather than on every timer tick, because the
transition is the event and the state can last for weeks; every entry into `RESYNC_REQUIRED` names
which of its four unrelated causes it was — a stale cursor, an unknown operation code, a changed
schema fingerprint, or the server asking — so that an unexplained bootstrap is attributable; and a
socket that reconnects forever, which is correct behaviour and looks identical to one that has never
connected, says which of the two it is.

**A log answers what happened; a snapshot answers what is true now.** `CollectionHandle.state` is
built for a user interface — four values, cheap enough to change many times a second — and it is
deliberately not where a developer looks when that interface has been saying "3 changes waiting" for
an hour. `diagnostics()` is: the queue itself, oldest first, with each group's state, its attempts,
its backoff and the error its last attempt was refused with, alongside the cursor, the generation,
the schema fingerprint and when a pull or a push last succeeded.

Almost all of it was already being written and none of it could be read. The collection's row has
carried `last_error` and `failure_count` from the beginning, and every group row its own
`last_error` and attempt count; nothing ever queried them, so the durable record of why a client
stopped was reachable only by opening the database file. That is the half of the problem a log does
not solve: `lastFailure` is deliberately in-memory, because a failure from a past process is history
— but a queue blocked since last Tuesday is precisely the case where nobody was watching when it
happened.

`isQueueBlocked` is on the snapshot rather than left to the caller because the distinction is easy
to get wrong and is the one that matters: a head serving a backoff is waiting and needs nobody,
while a head that is conflicted or refused has stopped and needs the application. Reporting the
first as stuck would make the signal useless for the second.

**No record carries an entity's document, at any level.** The library sends the application's
business data to the server and a diagnostic channel is the wrong place for it to reappear: a debug
build with a remote sink would export it, and debug logs are pasted into bug reports. Documents are
described by entity type, identifier, version and size. The HTTP tracing the SDK can install obeys
the same rule by construction — `SyncHttpTracing` has no entry for bodies — and it redacts
`Authorization` before writing a header.

## 10. The public API

Implemented in the `dev.voir.reflector.sync.core` package of `client-sdk`. The identifiers (`ScopeId`, `CollectionId`,
`EntityType`, `EntityId`) come from `contracts/sync-protocol`: they are the shared vocabulary
of client and server rather than a transport detail, and duplicating them would mean mapping
identity on every call.

```kotlin
interface SyncEngine {
    fun scope(scopeId: ScopeId): ScopeHandle
    suspend fun signOut(discardPending: Boolean)
}

interface ScopeHandle {
    val state: StateFlow<ScopeState>           // Online | Offline | AuthRequired | Revoked
    fun collection(id: CollectionId): CollectionHandle
}

interface CollectionHandle {
    val state: StateFlow<CollectionSyncState>  // phase, pendingCount, conflictCount, lastFailure
    suspend fun diagnostics(): CollectionDiagnostics   // the queue, the errors, the cursor — durable
                                               // phase: NEW | BOOTSTRAPPING | LIVE |
                                               //        NEEDS_ATTENTION | RESYNC_REQUIRED
    val conflicts: Flow<List<Conflict>>        // only what the adapter did not resolve itself
    suspend fun <R> mutate(block: suspend MutationScope.() -> R): R   // = withTransaction
    suspend fun adopt(entityType: EntityType, ids: List<EntityId>): Int  // pre-existing rows; §4
    suspend fun requestSync()
    suspend fun requestResync()                // drop the cursor and fetch the snapshot again
    val refusals: Flow<List<RefusedGroup>>     // groups refused for good, read from storage
    suspend fun discardLocalChanges()          // drop unsent work now, rebuild from the server; §8
    suspend fun resolve(conflictId: ConflictId, resolution: Resolution)
}

interface SyncEventChannel {                   // implemented by the transport, optional
    fun signals(scope: ScopeId): Flow<SyncChannelSignal>   // Connected | Received(event)
}

interface MutationScope {
    fun markUpserted(entityType: EntityType, id: EntityId)
    fun markDeleted(entityType: EntityType, id: EntityId)
}

interface CollectionAdapter {                  // implemented by the application
    val schema: SchemaFingerprint?                            // null — no declaration, see §9
    suspend fun snapshot(entityType: EntityType, id: EntityId): JsonObject?
    suspend fun applyRemote(ops: List<RemoteOp>)              // inside the library's transaction
    suspend fun onRejected(entityType: EntityType?, id: EntityId?, rejection: SyncRejection)
    suspend fun resolve(conflict: Conflict): Resolution?      // null — the user decides
}

interface TokenProvider {                      // implemented by the application
    suspend fun token(): String?
    suspend fun refresh(): Boolean
}

fun interface SyncTriggerSource {              // implemented by the application, optional
    fun triggers(): Flow<SyncTrigger>
}

fun interface SyncMetrics {                    // implemented by the application, optional
    fun record(event: SyncMetricEvent)
}
```

Three decisions in this API are worth naming explicitly.

`snapshot` returns a `JsonObject` rather than a `JsonElement`: the server merges the patch by
top-level keys, so anything other than an object is meaningless to it, and catching that with
a type is better than catching it with a server-side error.

`onRejected` accepts nullable `entityType`/`id`: a refusal may concern the group as a whole
(the envelope exceeded a limit), and attributing it to an arbitrary entity would be a lie.

`SyncRejection` is a set of its own rather than the code off the wire. The application needs an
exhaustive `when`, and `DEPENDENCY` never reaches it at all: the library answers that one by
merging groups. An unknown code becomes `SyncRejection.Unknown` and is treated as terminal.

## 11. Requirements on the server (the contract from the client's side)

1. A cursor is an opaque string. The client only stores it and hands it back.
2. Inside a collection there is a total order of changes, and the changelog is served with no
   omissions and no "visibility holes" (a change committed later cannot receive a seq lower
   than one already served to a client).
3. An entity's version is an opaque string; the client compares it only for equality.
4. `upsert` is a **patch-merge by the top-level keys present**: a missing field is left alone,
   an explicit `null` clears it. Nested objects are replaced whole. The client's serializer
   must write nulls explicitly (`explicitNulls = true`).
5. A push is idempotent by `groupId`: re-sending returns the stored result instead of applying
   it twice.
6. A group is applied atomically; groups in one request are independent.
7. `410` on a stale cursor, `409` when the collection was purged and began again, `403` when
   access to a scope is revoked, `429` with `Retry-After`.
8. The changelog carries `originClientId` — without it echo suppression is impossible.
9. Tombstones live at least as long as the declared retention window; that window is published
   so that a client can go to bootstrap early after a long offline stretch.
10. `GET /v1/sync/config` serves the effective limits and the retention window.
11. A snapshot item carries `entity`, `id`, `version` and `data`.
12. The set of operation codes in the log is fixed (`upsert`, `delete`); extending it is a
    breaking change, because the client rejects an unknown code with a resync.
13. `401` for an invalid token and `403` for revoked access to a scope are distinguishable.
14. Every answer names the collection's incarnation, and a cursor belongs to exactly one of them:
    a client must never be served a page of one log from a position in another.
