# Reflector — files (blob synchronisation)

The specification of the file extension: what travels beside the change log, who owns the bytes and
what the two existing specifications gain. The companion documents:
[the client specification](sync-client-design.md) and
[the server module specification](sync-server-design.md).

Nothing here changes the change log. A collection's cursor, its epoch, its batches, its versions and
its two operation codes are exactly what they were; files travel on a side channel at both ends, and
the only thing that crosses into the log is a list of identifiers on a push operation.

---

## 1. What this adds, and what it refuses to do

An application that synchronises a wallet also wants to synchronise the photograph of it. Today it
has three bad options: base64 into the document, which puts megabytes through a protocol designed
for kilobytes and into a `jsonb` column; a second, hand-written pipeline beside Reflector, which
duplicates the queue, the retries, the offline behaviour and the diagnostics; or nothing, and a
photograph that exists on one device.

What this adds is the **orchestration** of the third path, and only that:

| Responsibility | Whose |
| --- | --- |
| Deciding that a document references a file | The application |
| Holding the bytes on the device | The application |
| Holding the bytes on the server (S3, GCS, a disk) | The host |
| Presigning an upload or a download | The host |
| Validating the bytes: type, contents, virus, dimensions | The host |
| Processing an uploaded file: thumbnails, transcoding, OCR | The host |
| Knowing which files exist, and in what state | The module |
| Deciding when a file may be sent, and in what order | The library |
| Retries, backoff, resumption after a crash | The library |
| Knowing which files are garbage | The module |
| Deleting the garbage from storage | The host |

The library never opens a byte stream it did not get from the application, never writes one anywhere
but back into the application, and never touches object storage. On the server the module stores
**metadata about a file it has never seen**: an identifier, a size, a state and a storage key the
host handed it. That is the same relationship the module already has to business rows on the client
and to `jsonb` documents on the server — one step further, because here it does not even hold the
opaque bytes.

**The word.** What is synchronised is a **blob**: an immutable sequence of bytes with an identifier.
It is not a file — it has no name, no directory, no mtime and no place in a tree. An application
that wants a file name puts it in the document, where it belongs, next to everything else the user
typed.

## 2. Decisions taken

| Question | Decision |
| --- | --- |
| Mutability | A blob is immutable; replacing a file means a new blob |
| Identifiers | Generated by the client, like entity identifiers |
| Who knows a document references a blob | The application, through one adapter method |
| Where bytes travel | Directly between the device and the host's storage, never through the module |
| How the device reaches storage | A ticket: a presigned URL the host issues, opaque to both SDKs |
| Ordering against documents | Declared per reference: the record goes first by default, the file waits |
| A file that never uploads | The record stands; dropping the reference is an ordinary document change |
| Ordering against the log | Downloads never block a pull; a document arrives before its bytes do |
| Holding a file on the device | Declared per reference against one engine-wide default: eagerly, or only once the application asks |
| Acknowledgement of an upload | Three paths to one state, and one after-commit callback into the host |
| Blobs in the change log | Absent; blobs get no seq and no batch |
| Conflicts on blobs | None. Documents conflict; blobs cannot |
| Garbage | The module knows what is unreferenced; the host deletes it |
| Retention of an unreferenced blob | The same window as the log and the cursor |
| A purged collection | Takes its blobs with it, or the purge was a lie |
| Deduplication | Not the module's; content addressing is deliberately not used |
| Resumable and multipart uploads | Not built; the ticket's shape leaves room |
| Encryption | None, as for documents: the host sees plaintext |
| Opting in | Entirely. An integration that declares no blob store never calls a blob path |

## 3. The model

```
scope
└── collection                       — a blob belongs to one collection, like an entity
    ├── entity (wallet 7f3…)         — its document references blobs by identifier
    └── blob (b1a…)                  — immutable bytes, uploaded once, never rewritten
```

A blob is addressed by `(scope, collection, blobId)`. It is not addressed by entity: two entities
may reference the same blob, and an entity may reference several. The relation between them —
**the reference** — is derived from the document by the application and recorded on both sides.

The document holds whatever the application wants:

```jsonc
{"title": "Holiday", "currency": "EUR", "photoBlobId": "018f…"}
```

Neither SDK parses that. The application answers one question about it:

```kotlin
public fun blobs(entityType: EntityType, id: EntityId, document: JsonObject): Set<BlobRef>
```

A `BlobRef` is an identifier and two words about it: a **binding** — whether the record may go
out ahead of its file, or has to wait for it — and a **fetch policy**, whether a device that
receives the record fetches the file straight away or waits to be asked. Section 4 is about both,
and they are the two halves of one question: what a record is worth without its file.

That is the entire coupling between business data and file synchronisation, and it is the same
shape the rest of the library already uses: the application owns the meaning, the library owns the
bookkeeping. The alternative — the library scanning documents for a marker field, or a magic
`"$blob"` wrapper — would put the library back in the business of understanding the application's
schema, which it spends the rest of both specifications refusing to do.

### Why a blob is immutable

This is the decision everything else rests on, exactly as state-based change is for documents.

An immutable blob cannot conflict. There is no version to compare, no base version to refuse, no
merge to ask a user about — and there could be no merge anyway, because two JPEGs have no common
ancestor a program can reason about and no meaningful union. Under mutable blobs every question the
document layer answers would have to be answered again, worse: what a `baseVersion` on 4 MB means,
what the server does with a stale write it cannot merge, what a client shows while the bytes it has
are known to be old.

Immutability also makes every operation on a blob idempotent. A re-sent upload is the same upload. A
download replayed after a crash produces the same bytes. A snapshot that mentions a blob the device
already has is a no-op. None of that has to be engineered; it follows.

The price is that editing a photograph writes a new blob and leaves the old one garbage, which is
why section 7.4 exists. That is a cost paid in storage, which is cheap, instead of in correctness,
which is not.

### Why identifiers are the client's

The same reason entity identifiers are: a photograph taken in a tunnel has to have an identity
before anything reaches a server, and the document that references it is written in the same local
transaction. A server-assigned key would mean the document cannot be written until the device is
online, which is the one thing an offline-first library exists to avoid.

UUIDv7 is the recommendation and nothing enforces it, as for entities.

### Why not content addressing

A blob identified by the hash of its contents would deduplicate for free and make the immutability
structural rather than declared. It is not used, for three reasons, in order of weight:

1. the device would have to hash the whole file before it could write the document that references
   it — a full read of a large file on the UI path, and a hash function the Kotlin standard library
   does not have on every target;
2. deduplication across scopes is an access-control question disguised as a storage optimisation:
   two users who upload the same file would share one object, and whether that leaks anything is
   the host's decision to make, not the module's to take by construction;
3. a host that wants deduplication can have it without the protocol knowing — it maps its own
   storage key by checksum inside `BlobStorage`, which is exactly where that decision belongs.

## 4. Ordering: the record first, the file when it can

Every attachment forces one question: what happens to the record while its file is still moving, or
is never going to move at all.

A receipt is not a transaction. Money changing hands is a fact the other devices need now, and a
photograph of the till roll is an improvement on it. A library that refuses to record the transaction
because a 6 MB JPEG is stuck behind a hotel's captive portal has its priorities backwards, and it
would have them backwards in exactly the cases that matter most.

So a reference carries a **binding**, chosen by the application, per reference:

| Binding | The document | For |
| --- | --- | --- |
| `DEFERRED` (default) | goes out immediately; the file appears on the other devices when its bytes land | a receipt, an avatar, a photograph of a wallet — anything the record survives without |
| `REQUIRED` | is held in the queue until the blob is `READY` on the server | a record whose file *is* its content: a photo post, a voice message, a scanned contract |

**`DEFERRED` is the default, because the common case is that the record matters more than the file.**
An integration that thinks about none of this gets the behaviour that cannot lose anything
important: the transaction is recorded now, and the receipt arrives late, or never.

**What `DEFERRED` still waits for is one round trip, and it cannot not.** The server refuses a
document that names a file it has never heard of, so the file has to be **registered** before the
record that points at it goes out. That is a request and an answer, not a transfer: the bytes may
take minutes afterwards and the record does not wait for them. `REQUIRED` waits for the bytes as
well, and that is the whole difference between the two in the queue.

A file already given up on holds nothing back. It is never going to be registered, the reference is
the application's to withdraw, and in the meantime it is simply left out of the envelope — there is
nothing on the server for it to protect.

`REQUIRED` buys one thing — that no device ever sees a record in a state where it means nothing; a
post with no image is not a post — and it pays head-of-line blocking for it. The group waits, and
because the queue is FIFO, everything behind it waits too. That is the right trade only when the
record without its file would be worse than no record at all, which is rarer than it first sounds.

**What the binding does not change: the library never edits the application's document.** If the
transaction's document says `receiptBlobId: B1`, every device sees that field from the first push,
under either binding. The binding decides whether the push **waits** — not what the document says.

Which means a deferred attachment lands the second device in a state it already has to handle: a
blob that is referenced and not here yet, exactly as a large photograph is while it downloads. A
placeholder, a spinner, and the per-blob state flow to drive them. There is no second case for an
application to write, and that is the main reason this is one word on a reference rather than two
mechanisms.

**The receiving side never waits, under either binding.** A document arrives, is applied, the cursor
advances, and the bytes are fetched afterwards. Blocking a pull on a download would stop a whole
collection because one photograph is large, and it would buy nothing: the receiving device cannot
repair a missing blob, so there is no decision to protect.

**An upload that fails for good is repairable, deliberately.** The application is told through
`BlobStore.onFailed`, and what it does about it is an ordinary document change: drop the field in a
new `mutate`, and the reference disappears from every device. Under `DEFERRED` the record was never
at risk to begin with. Under `REQUIRED` the queue is blocked until that correction is made — which
is precisely the cost that binding announces, and the reason it is not the default.

### The same question from the other end: what the receiving device holds

A binding decides whether a record waits for its file. It says nothing about the device the record
arrives on, which faces the other half of the same question: a wallet is here, it names a
photograph, and fetching it costs the user's bytes and the user's storage.

Fetching everything is the right answer often enough to be the default and wrong often enough to
need a second word. A thumbnail in a list is wanted before anybody asks for it; the forty-megabyte
original beside it is wanted by the one screen that opens it, and a device that pulls every original
of every record has spent a gigabyte to be ready for a tap that will not come.

So a reference carries a **fetch policy** as well, chosen by the application:

| Policy | This device | For |
| --- | --- | --- |
| `EAGER` (default) | fetches the bytes as soon as a document names them | a thumbnail, an avatar, a photograph of a wallet — anything a list draws |
| `ON_DEMAND` | records the reference, fetches nothing, and waits for `CollectionHandle.fetch(blobId)` | an original, a scan, a video — anything large enough that holding it unasked is a cost |

**A policy left unstated takes the engine's**, which is one parameter of `SyncEngine(...)` and also
defaults to `EAGER`. That is the shape the choice actually has in an application: one answer for
almost every file, and a different one for the two references that are large. An integration that
thinks about none of it keeps exactly the behaviour it had before the policy existed.

**Eager wins where two documents disagree** about the same blob. It is the only reading under which
a record that cannot be drawn without its file reliably has it, and the cost of being wrong the
other way is one file held that did not need to be.

**What `ON_DEMAND` does not change is what the record says.** The document names the file from the
first push, as under either binding, and the reference row exists from the moment the document is
applied — so garbage collection cannot take the blob out from under it, and every device agrees on
what points at what. What differs is one bit on this device: whether anything is trying to get the
bytes.

**Nothing on the wire changes.** The download ticket is already fetched one blob at a time, on
demand, by a device that decided it wants one; asking later rather than at once needs no new
endpoint, no new field and no new event. `blobReady` still arrives for a file nobody asked for, and
is answered by ignoring it.

The prices, stated plainly:

- **A file left unfetched has never been described.** Its size, its media type and its checksum are
  declared by the ticket response, and there has not been one. A screen that wants to say *2.4 MB*
  before offering the download takes that from its own document, where the application put it when
  it attached the file. The library will not fetch metadata it was told not to fetch.
- **A mistake in the application's references surfaces late.** The third line of the arithmetic in
  6.3 — referenced, bytes absent, the server has never heard of it — is discovered by trying, and
  under `ON_DEMAND` nothing tries until somebody opens the record.
- **What is fetched stays fetched.** The library evicts nothing on its own: no ceiling, no
  least-recently-used, no policy it invented about somebody else's storage. A device that fetches on
  demand and wants the space back asks for it, through `CollectionHandle.evict(blobId)`, and the
  file goes back to being one the server has and this device does not.

## 5. The wire protocol

Three endpoints, one field on a push operation and one event on the existing socket. Everything
else is unchanged.

```
POST /v1/sync/{scope}/{collection}/blobs                   → register, and get an upload ticket
POST /v1/sync/{scope}/{collection}/blobs/{blobId}/complete → the bytes are up; verify and accept
GET  /v1/sync/{scope}/{collection}/blobs/{blobId}          → get a download ticket
```

```jsonc
// POST …/blobs                                                        — body: BlobDescriptor
{"blobId":"018f…","contentType":"image/jpeg","size":2418123,"checksum":"sha256:9f…"|null}
// → 200                                                               — BlobRegistration
{"blob":{"blobId":"018f…","state":"pending","contentType":"image/jpeg",
         "size":2418123,"checksum":"sha256:9f…"},
 "upload":{"method":"PUT","url":"https://…","headers":{"Content-Type":"image/jpeg"},
           "expiresAt":"2026-09-15T12:34:56Z"}}
// → 200 with "state":"ready" and "upload":null, when the blob is already there (idempotent)
// → 409 when the identifier is known with different bytes (size or checksum disagree)
// → 413 when the size exceeds the published limit

// POST …/blobs/{blobId}/complete                                      — body: {}
// → 200 BlobInfo: {"blobId":"018f…","state":"ready","contentType":"image/jpeg","size":2418123,…}
// → 409 when the host cannot find the object, or it disagrees about size or checksum

// GET …/blobs/{blobId}                                                — BlobDownload
// → 200 {"blob":{…,"state":"ready"},
//        "download":{"method":"GET","url":"https://…","expiresAt":"…"}}
// → 200 {"blob":{…,"state":"pending"},"download":null}  — registered, still uploading
// → 404 when the blob is unknown, collected, or belongs to another collection
```

`BlobInfo` is the one shape both answers are built from, rather than each repeating the same five
fields: a registration is it plus the permission to send, a download is it plus the permission to
fetch, and `complete` is it alone. One ticket type serves both directions — they differ in the
method they carry, and two structurally identical classes would be ceremony rather than safety.

**"Not ready yet" is a state in a `200`, not a status code.** The sync endpoints already spend `409`
on a purged collection and `410` on a stale cursor, and a fourth meaning for a refusal code on a
neighbouring path is how a client ends up mapping one of them wrong. The blob exists; it is simply
not servable — that is information, not a failure, and the response says so in the field it already
has.

The field, on a push operation:

```jsonc
{"entity":"wallet","id":"…","op":"upsert","baseVersion":"41",
 "data":{…},
 "blobs":["018f…"]}        // null = this client does not track blobs; [] = references none
```

It carries **every** blob the document references, whether or not the bytes have landed yet. That is
what makes `DEFERRED` safe: a blob registered but still uploading is recorded as referenced from the
moment the record is pushed, so garbage collection cannot take it out from under a document that
already names it. The reference does not have to be "activated" later — the ref row exists, and the
blob's own state says whether it can be served yet.

**`blobs` is three-state on purpose**, the same way a document field is. `null` means the client has
nothing to say and the server leaves its reference rows alone; `[]` means the document references no
blob and the server drops them. Collapsing the two would make the first push from a client that
predates this extension look like "everything is unreferenced now", and garbage collection would
delete blobs that are still in use. `SyncProtocolJson` already writes nulls explicitly, so the
distinction survives the wire.

A new refusal code joins the set:

```
BLOB_MISSING — an operation references a blob this collection has never heard of
```

Never heard of, rather than not ready: a blob that is registered and still uploading is accepted, or
`DEFERRED` could not work. What is refused is a reference to an identifier that was never registered
— a typo, or a client inventing one — and to one that has been collected as garbage, which is what a
client meets when a group sat blocked for longer than the retention window. It is the second code
after `DEPENDENCY` that a retry can fix, and the client's answer is specific: mark those blobs as not
uploaded, upload them again, and re-send the group under a new identifier.

**One event joins the scope's socket**, for the same reason the socket exists at all:

```jsonc
{"type":"blobReady","collection":"ledger","blobId":"018f…"}
```

It is an alarm clock, not data — the device answers it by retrying that blob's download. Without it
a deferred attachment would appear on the other devices whenever their backoff next happened to
fire, which is minutes of a photograph that is sitting ready in a bucket. Adding it costs nothing in
compatibility: an event a client does not know is already defined as a generic invalidation, so an
older client answers it with one harmless extra pull.

**The limits grow a nested, nullable block:**

```jsonc
// GET /v1/sync/config
{"maxOperationsPerGroup":500,"maxDocumentBytes":262144,"maxChangesPageSize":500,"retentionDays":30,
 "blobs":{"maxBlobBytes":26214400,"maxBlobsPerEntity":16,"uploadTicketSeconds":900}}
```

`blobs: null` means this server does not serve blobs. A client configured for them then fails at
start-up with a clear statement instead of discovering it as a `404` on the first photograph, and a
client that is not configured for them never looks.

**The epoch does not appear on a blob path.** A purge deletes the collection's blob rows with
everything else, so a device still holding the old incarnation gets `404` on its blobs and `409` on
its very next `push`, `changes` or `snapshot` — which is the answer that matters, and the one that
wipes. Carrying the epoch on three more endpoints would buy a slightly earlier version of the same
outcome.

## 6. What the client does

### 6.1 The ports

Two new ports, and one method on an existing one.

```kotlin
/** Implemented by the application. Where the bytes live on the device. */
public interface BlobStore {
    public suspend fun stat(blobId: BlobId): BlobStat?                    // size, type, checksum
    public suspend fun read(blobId: BlobId): RawSource                    // for an upload
    public suspend fun write(blobId: BlobId, stat: BlobStat): RawSink     // for a download
    public suspend fun finish(blobId: BlobId, complete: Boolean)          // keep it, or discard it
    public suspend fun remove(blobId: BlobId)                             // nothing references it
    public suspend fun onFailed(blobId: BlobId, failure: BlobFailure)     // it will not arrive
}

/** Implemented by the transport; the Ktor one ships. */
public interface BlobTransport {
    public suspend fun register(scope, collection, descriptor: BlobDescriptor): BlobRegistration
    public suspend fun complete(scope, collection, blobId: BlobId): BlobInfo
    public suspend fun ticket(scope, collection, blobId: BlobId): BlobDownload
    public suspend fun upload(ticket: BlobTicket, content: RawSource, stat: BlobStat, onProgress)
    public suspend fun download(ticket: BlobTicket, into: RawSink, onProgress): Long
}

/** On the existing adapter, defaulted, so no current integration changes. */
public interface CollectionAdapter {
    public fun blobs(entityType: EntityType, id: EntityId, document: JsonObject): Set<BlobRef> = emptySet()
}

/** What a document points at, whether the record may go out without it, and who fetches it. */
public data class BlobRef(
    val id: BlobId,
    val binding: BlobBinding = BlobBinding.DEFERRED,
    val fetch: BlobFetch? = null,      // null = whatever the engine was configured with
)

public enum class BlobBinding { DEFERRED, REQUIRED }

public enum class BlobFetch { EAGER, ON_DEMAND }
```

`BlobBinding.DEFERRED` is the default value of the parameter as well as the default of the design,
so `BlobRef(id)` is the short and the safe spelling, and an application reaches for `REQUIRED` only
when it has decided that the record is not worth publishing without its file.

`BlobFetch` is nullable where `BlobBinding` is not, and the asymmetry is deliberate. A binding is
a statement about one record and has no sensible fleet-wide answer; a fetch policy is almost always
one answer for a whole application — hold everything, or hold what is asked for — with two or
three references that differ. So the engine takes the default (`SyncEngine(blobFetch = …)`, itself
defaulting to `EAGER`) and `null` here means the application has nothing to add about this
particular reference. The policy is resolved once, in the transaction that writes the reference row,
so nothing below this line ever has three cases to consider.

A download hands back a **sink** rather than returning a source, and is followed by `finish`. The
application writes somewhere temporary and moves the file into place only when `finish` says the
bytes arrived in full and matched what was promised — otherwise a download interrupted halfway
leaves a truncated file exactly where the application's own code will find it and believe it.

`upload` and `download` are on the transport rather than left to the application because a presigned
URL is a plain HTTP request that must **not** carry the scope's `Authorization` header, must not go
through content negotiation and must stream rather than buffer. That is three ways to get it subtly
wrong in every integration, and the SDK already owns an HTTP client. Sending the scope's credentials
to a ticket would hand a bearer token for the user's whole scope to a storage provider, on every
photograph, and nothing downstream would notice — so the ticket path never goes through the code that
attaches them, and a test asserts the header's absence.

`BlobStore` is where every application-facing blob callback lives, rather than on `CollectionAdapter`,
because an application with no files does not implement it at all — and then no blob path in the
library is ever entered. Opting in is the presence of the port.

**The library never deletes the user's bytes on its own.** `remove` is an offer, not an order: it is
called when nothing synchronised references the blob any more, and an implementation that keeps the
file for an undo stack is correct. The exceptions are sign-out, revocation and a purge, where removal
is not eviction but the same act as wiping the scope's rows, and the library calls `remove` for every
blob concerned. Leaving a signed-out user's photographs on a shared device is not a policy question.

Revocation reaches it through sign-out, which is how an application answers one. A store that throws
there is logged and passed over and the rows go regardless: a scope that could not be wiped because
one file refused to be deleted would leave the user signed in.

### 6.2 The schema

Two tables, in the application's database beside the rest, for the same reason as the rest:
reference rows are written in the transaction that applies a batch.

```sql
sync_blob(
  scope_id TEXT, collection_id TEXT, blob_id BLOB(16),   -- PK
  state TEXT,                  -- LOCAL | UPLOADING | UPLOADED | REMOTE | DOWNLOADING | READY | UNAVAILABLE
  wanted INTEGER NOT NULL DEFAULT 0,        -- whether this device is trying to hold the bytes
  content_type TEXT NULL, size INTEGER NULL, checksum TEXT NULL,
  attempts INTEGER NOT NULL DEFAULT 0, next_retry_at INTEGER NULL, last_error TEXT NULL,
  transferred INTEGER NOT NULL DEFAULT 0    -- bytes moved, for progress only
);

sync_blob_ref(
  scope_id TEXT, collection_id TEXT, entity_type TEXT, entity_id BLOB(16), blob_id BLOB(16), -- PK
  binding TEXT NOT NULL,       -- DEFERRED | REQUIRED, as the adapter declared it
  fetch TEXT NOT NULL DEFAULT 'EAGER',      -- EAGER | ON_DEMAND, resolved by the engine
  seen_gen INTEGER NOT NULL
);

-- Both tables are part of the library's schema whether or not an application synchronises files.
-- An application that implements no BlobStore leaves them empty, which costs two empty tables and
-- saves every consumer a second `@Database` shape to choose between.
CREATE INDEX ix_sync_blob_ref__scope_id__collection_id__blob_id
  ON sync_blob_ref(scope_id, collection_id, blob_id);
```

The states and what they mean:

| State | The bytes | The server |
| --- | --- | --- |
| `LOCAL` | on the device | does not know it |
| `UPLOADING` | on the device | registered, receiving |
| `UPLOADED` | on the device | `READY` |
| `REMOTE` | not here | `READY` |
| `DOWNLOADING` | arriving | `READY` |
| `READY` | on the device | `READY` |
| `UNAVAILABLE` | gone or unreachable | unknown |

`UPLOADED` and `READY` are the same server-side fact reached from the two ends, and they are kept
apart because only they say the bytes were ever on this device too. No ticket is ever stored: a
presigned URL is a bearer capability with a short life, and a database row is the wrong place for
both halves of that sentence.

**`wanted` is a column and not a state**, and that is the one modelling decision the fetch policy
makes. The state says where the bytes are; `wanted` says whether anything is trying to change that.
Folding the two together would produce a state that means "on the server, not here, and nobody
asked" and immediately need a second one for "…and somebody did" — and then `UNAVAILABLE` would
have to be split as well, because a file given up on either was asked for or was not, and a retry
has to know which. As a separate column it survives every transition the state makes, which is what
makes a request durable: a download interrupted by the process dying resumes rather than waiting to
be asked again.

The download queue is exactly the rows where both agree that bytes are missing and wanted. Uploads
need no second predicate, because **bytes on this device are wanted by construction** — they are
already holding the space, and the only thing left to do with them is send them.

`wanted` is set by an eager reference, by `CollectionHandle.fetch`, and by the bytes being here; it
is cleared only by `CollectionHandle.evict` and by the row's own removal. Nothing a document does
clears it, which is the point: a reference the application edits must not be able to discard a
request the user made.

**Invariants**

- A reference row exists if and only if the application's answer to `blobs(...)` said so at the last
  time that entity's document was materialised or applied.
- `sync_blob.wanted` is true whenever the bytes are on this device, and false only for a file the
  server has, this device does not, and nothing has asked for.
- A blob row with no reference row is garbage: under either binding the reference is declared by the
  document that names it, and the document is what brings the blob to the library's attention.
- `sync_blob_ref.seen_gen` takes part in the bootstrap sweep exactly as `sync_record.seen_gen` does.
- No transfer runs inside a database transaction. Ever.

### 6.3 Where references come from

There is one rule, applied at every moment a document passes through the library, each time inside
the transaction that wrote it:

- **at push time**, right after `adapter.snapshot(...)` returns the document that is about to be
  sent, and inside the same transaction that assembles the envelope;
- **at apply time**, for every `RemoteOp.Upsert` handed to `adapter.applyRemote(...)`, inside the
  transaction that applies the batch and advances the cursor;
- **at bootstrap**, for every snapshot item, with the sweep taking the references of documents the
  snapshot did not mention;
- **when a conflict is resolved**, because taking the server's wallet takes its photograph too.

In every case the entity's reference rows are replaced wholesale by the answer, which is what makes
this state-based like everything else: there is no "reference added" or "reference removed" event to
lose. A `RemoteOp.Delete` removes the entity's rows.

**Only the reference is written there.** Whether the bytes are on this device is a question for the
application's own store, and that is not a question to ask with a write lock held — so a reference
exists for a moment before anything is known about the file it names, and the arithmetic below is a
second pass that runs between transactions:

```
referenced, bytes present, server does not know it       → upload
referenced, bytes absent,  wanted here                   → download
referenced, bytes absent,  declared Eager by any document → want it, then download
referenced, bytes absent,  wanted, server knows nothing  → the application made a mistake: onFailed
not referenced anywhere, bytes present                   → offer BlobStore.remove
```

The third line is a statement of its own rather than a clause of the second, because it runs on
every pass over the two tables and not only when a file is first discovered. A document edited into
naming a file eagerly, a second document that names one the first declared on demand, and a file
evicted although a declaration says this device keeps it all arrive after the file was adopted, and
all three are settled by asking the reference rows again — one statement, no per-file query, and
nothing remembered between passes.

That pass runs **after every cycle, whatever the cycle achieved** — not at the end of one. A cycle
stops early for half a dozen ordinary reasons, and a push that was refused is exactly the moment at
which a file the same cycle just referenced still has to be looked into. Everything the pass decides
is derived from the two tables rather than from anything it remembers, so an interrupted run leaves
work for the next one and repeats nothing.

**A file is offered back before the library forgets it.** `BlobStore.remove` is called first and the
row is dropped only if the application did not throw. The other order would mean an application that
failed to hear is never told again, and its file is then accounted for by nobody.

### 6.4 The blob worker

Each collection gets a third coroutine beside its cycle. It is separate because a transfer is long
and the cycle must stay answerable, and it holds no state the database does not: attempts, backoff
and progress are rows, so a process killed mid-upload resumes rather than restarts the queue.

```
uploads:   blobs in LOCAL or UPLOADING that any reference row names, bounded concurrency (2)
downloads: blobs in REMOTE or DOWNLOADING that a reference names and something wants,
           bounded concurrency (2), only once uploads are drained
```

An upload is driven by the reference, not by the queue: a deferred attachment uploads while its
record is already on the server, and its entity is long since clean. Uploads are drained before
downloads are looked at, because a record waiting on a file it cannot be published without is the
only thing here that blocks a queue on bytes — everything else is somebody's photograph arriving.

A row left `UPLOADING` or `DOWNLOADING` by a process that died is not a special case. Registering is
idempotent by identifier, so asking again produces a fresh ticket for the same object and the bytes
go out a second time; that is the whole of the crash recovery, and it is why no state beyond the row
is kept.

**When an upload lands, the push queue is told.** A group held back by a `REQUIRED` reference has no
other way of learning that its file arrived — the queue has no reason of its own to look again — so
without that the record would sit until the next timer, which on a device nobody touches is however
long that is.

The push's `prepare()` gains one check before it builds an envelope: if any entity of the head group
holds a **`REQUIRED`** reference to a blob **the server does not have**, the group is not ready, and
the outcome is the existing `Waiting` — logged with the reason, the blob and the bytes left, so that
"why is nothing leaving this device" has an answer here too. A deferred reference never holds a
group, which is the whole of what `DEFERRED` means in code.

**"The server does not have it" is the question, not "this device has sent it".** `UPLOADED` and
`READY` answer it, and so do `REMOTE` and `DOWNLOADING`: a file that arrived from another device is
on the server by definition, whether this device has fetched the bytes or has declined to. Asking
for `UPLOADED` alone would hold a group for a download nobody asked for — and under `ON_DEMAND` would
hold it for good, because that download is never going to start. What still holds a `REQUIRED` group
is `LOCAL`, `UPLOADING` and `UNAVAILABLE`, which is the cost that binding announces.

An upload is three calls and a state each: `register` → `UPLOADING`, `upload` (straight to the
host's storage), `complete` → `UPLOADED`. A crash between any two of them is recovered by repeating
from the row's state, and every one of the three is idempotent by `blobId`.

A file nothing wants is not in the queue at all, so `ON_DEMAND` costs the worker nothing: no request
is made, no backoff runs, and `blobReady` for such a file is answered by finding nothing to do.
Asking for one — `CollectionHandle.fetch` — writes the wish and wakes the worker, which is the same
path a newly adopted file takes. Asking for one the library has given up on puts it back to `REMOTE`
with no attempts and no error, because the user asking again is the only thing that can restart
it; asking for one that is merely serving a backoff changes nothing, because a screen redrawing
itself is not new information about a transfer that keeps failing.

A download of a blob the server holds as still uploading — the ordinary state of a deferred
attachment the moment its record arrives — comes back as `state: pending` with no ticket, and is
retried on a capped backoff, or at once when the scope's socket delivers `blobReady` for it. That
event goes straight to this worker rather than to the cycle: nothing about the log has changed, so a
pull would not discover it. The two together are why a receipt taken on one phone appears on the
other in seconds rather than at whatever minute the backoff lands on, and why it still appears if
the socket was down.

A download that ends short of what was promised is discarded through `BlobStore.finish(complete =
false)` **before** anything else, so a truncated file never sits where the application's own code
will find it and believe it.

**`404` and `409` mean something different on a blob path than anywhere else in this protocol**, and
the transport reads them itself rather than through the shared mapping: `404` is a file the server no
longer has, and `409` is a file it refuses. Passed through the shared mapping, a failed upload would
have been read as a purged collection and wiped the collection it belonged to.

### 6.5 What the application can see

```kotlin
public interface CollectionHandle {
    public fun blob(id: BlobId): Flow<BlobSyncState?>    // null until a document names it
    public suspend fun fetch(id: BlobId)                 // bring the bytes here
    public suspend fun evict(id: BlobId)                 // give them up; the server keeps the file
}

public data class BlobSyncState(state, wanted, size, transferred, lastError)

public data class CollectionSyncState(
    val pendingBlobs: Int,        // files this device holds and the server does not
    val incomingBlobs: Int,       // files the server has, this device wants, and does not have yet
)
```

`blob(id)` is what a photograph in a list binds to, which is the one case where per-item state is
worth a flow: the UI already knows which identifier it is rendering, and the alternative — a list of
every blob in the collection — is the wrong shape for the only screen that needs it.

**`state` and `wanted` together are what a screen switches on**, and neither is enough alone.
Bytes here — `LOCAL`, `UPLOADING`, `UPLOADED`, `READY` — is a file to draw. `REMOTE` while nothing
wants it is an offer to download. `REMOTE` or `DOWNLOADING` while something does is a spinner and a
fraction. `UNAVAILABLE` is the one failure a user can act on, and the action is `fetch` again. There
is no fifth case, and none in which the two fields disagree about what to draw.

`fetch` is idempotent and safe on every redraw; `evict` is refused for a file whose bytes are the
only copy — one this device created and has not finished uploading — because freeing a cache and
losing the user's file are not the same act, and only the row's state tells them apart. Neither is
an instruction to transfer anything now: they record what this device wants, and the worker does the
rest, which is the shape every other call in this library has.

**A file no document references is not fetched, whoever asks.** The library would have nothing to
keep it for and reconciliation would offer it straight back, so the request is logged and dropped
rather than half-honoured.

**The two counts are apart from `pendingCount` because they mean different things to a user.** A
record that has not reached the server is work that could be lost; a photograph that has not is a
slow upload. An application that added them together would ask somebody not to close the app over a
holiday video.

**`incomingBlobs` counts what is wanted, not what is referenced.** Under `ON_DEMAND` most files
are referenced and absent for as long as the record exists, and counting those would have an
application reporting a dozen arrivals that nothing is waiting for. What is counted is work in
progress, which is the only reading a progress indicator can be built on.

**What the state publishes is `lastError`, a description — not the typed `BlobFailure`.** The typed
failure is a decision, and it is delivered where decisions belong: once, to `BlobStore.onFailed`, at
the moment nothing more will be tried. A value in `lastError` while the state is still moving means
an attempt failed and another is coming, and a screen that treated it as final would tell the user a
photograph was lost every time a train went into a tunnel.

`CollectionDiagnostics` gains `files`, with each one's state, attempts, backoff, last error,
whether anything still references it and whether this device wants it — and
`isQueueWaitingOnFiles`, which is the question the rest of the snapshot cannot answer. A collection
can be perfectly healthy, nothing conflicted and nothing refused, and still send nothing at all,
because its oldest group holds a record bound to a file that is still moving. That is working as intended and is invisible in every other value there; without
the question, the only honest description of such a collection is that it is stuck for no reason.

Unlike the group queue, the file list is not an ordering and its first entry explains nothing: what
is worth reading is the entries whose attempts are climbing, the ones nothing references any
more — a list of those on an otherwise idle collection means the application is declining to take
the files it is offered — and the referenced entries nothing wants, which are the files this device
has decided not to hold and are the one thing in the list that is idle on purpose.

## 7. What the server module does

### 7.1 The ports

```kotlin
/** Implemented by the host. The module never touches storage. */
public interface BlobStorage {
    public fun keyFor(scope, collection, blob: BlobDescriptor): BlobStorageKey
    public fun createUpload(scope, collection, blob: StoredBlob): BlobTicket
    public fun createDownload(scope, collection, blob: StoredBlob): BlobTicket
    public fun verify(scope, collection, blob: StoredBlob): BlobVerification
    public fun onReleased(scope, collection, blobs: List<StoredBlob>)             // these are yours
}

/** Called after the commit that made a blob usable. The acknowledgement. */
public fun interface BlobListener {
    public fun onBlobReady(scope: ScopeId, collection: CollectionId, blob: StoredBlob)
}
```

`BlobTicket` is `{method, url, headers, expiresAt}` and nothing else. The module does not know
what S3 is, and a host that presigns GCS, or signs its own upload endpoint, or serves a local
directory in tests, is indistinguishable from here. `verify` is a `HEAD`: the host observes and
reports, and the module compares the answer with what the client declared. A checksum the storage
cannot report is not a disagreement — plenty of them cannot — and the size comparison still applies.

Naming the object is a method of its own because the module needs a key before it has a blob to
presign for, and presigning needs a blob that already has one. The split is also what keeps the next
rule absolute: `keyFor` is a pure local decision, so it can be asked before the module knows whether
it will need the answer.

**No method here is ever called inside one of the module's transactions.** Each operation reads what
it needs, lets the transaction go, talks to the host, and opens a second transaction to write the
outcome — which is why every write on this path is conditional on the state it expects rather than on
what was read a moment earlier. An implementation is free to reach the network, and a database
connection held across that is how a backend deadlocks itself under load.

**`onReleased` is a notification, not an instruction, and that is the whole of its contract.** The
module has already dropped its rows by the time it is called; what it says is "nothing points at
these any more, here are their keys, they are yours". It asks for nothing back and forms no opinion
about what happens next.

That is deliberate, because disposal is a policy and the module has no business holding one. Deleting
at once, tagging for a lifecycle rule, keeping the object for a retention period a regulator set, or
doing nothing because the bucket already has a rule of its own are all correct — and a port that
demanded a list of what had been deleted would report three of them as a fault.

The division of labour is the reverse of how it first looks. Deciding **which** objects are garbage
has to be the module's: only it holds the references, and to the host a document is opaque `jsonb`.
Deciding **what disposal means** has to be the host's: only it knows what the storage is for, what
its regulator requires and what its bucket already does. `onReleased` is where the first hands over
to the second.

### 7.2 The schema

```sql
sync.blobs (
  id                 uuid          primary key,
  collection_id      uuid          not null references sync.collections on delete cascade,
  blob_id            uuid          not null,
  state              varchar(20)   not null,     -- PENDING | READY, by name and never by ordinal
  storage_key        varchar(1024) not null,     -- what the host called it; opaque here
  content_type       varchar(255)  not null,
  size               bigint        not null,
  checksum           varchar(200)  null,
  created_at         timestamptz   not null,
  ready_at           timestamptz   null,
  unreferenced_since timestamptz   null,          -- null = something references it
  constraint uq_blobs__collection_id__blob_id unique (collection_id, blob_id),
  constraint ck_blobs__ready_at_matches_state check ((state = 'READY') = (ready_at is not null)),
  constraint ck_blobs__size_is_not_negative check (size >= 0)
);
create index ix_blobs__collection_id__unreferenced_since
  on sync.blobs (collection_id, unreferenced_since);

sync.blob_refs (
  collection_id uuid         not null,
  entity_type   varchar(100) not null,
  entity_id     uuid         not null,
  blob_id       uuid         not null,
  constraint pk_blob_refs primary key (collection_id, entity_type, entity_id, blob_id),
  constraint fk_blob_refs__collection_id__blob_id__blobs
    foreign key (collection_id, blob_id)
    references sync.blobs (collection_id, blob_id) on delete cascade
);
create index ix_blob_refs__collection_id__blob_id
  on sync.blob_refs (collection_id, blob_id);
```

**A reference row carries no identifier of its own.** It is a pure association with no lifecycle and
nothing that could address it, so its natural key is all four columns and a surrogate would be a
column nothing would ever read.

**What the client declared is stored as not-null**, because the registration that created the row
had to carry all of it: a blob whose size nobody stated could not be refused for exceeding a limit,
and one whose media type nobody stated could not be served back correctly. Only the checksum is
optional, and its absence is the documented weakening of verification to a size comparison.

**The cascade from a blob to its references is the one place hard deletion is right**: a reference
cannot exist without the blob it names. It is not what protects a blob in use from being collected —
`unreferenced_since` is — and it is also what keeps a purge simple, since the cascade from
`sync.collections` then reaches both tables.

A blob has no version, no seq and no epoch. It is not in the log, it is not in a batch, and a
client's cursor says nothing about it — which is exactly why none of the ordering machinery of §6 of
the server specification applies to it, and why nothing in that machinery had to change.

### 7.3 The three ways a blob becomes ready

The acknowledgement the host waits for has one meaning and three paths to it, because a device that
finished a `PUT` is the fastest witness and the least reliable one.

All three are the **same method**, `SyncBlobService.markUploaded`, reached from three directions:

1. **The client says so.** The host publishes `POST …/complete` over it.
2. **The host's storage says so.** An S3 event notification, an SQS consumer, a Lambda — whatever
   the host already has — calls it directly. This is the one that survives a device dying between
   the `PUT` and the `complete`.
3. **The sweep says so.** A blob left `PENDING` past the ticket's life is confirmed through the same
   call during maintenance, and either becomes usable or is left for collection.

It asks `BlobStorage.verify`, compares the answer with what was declared, and promotes the blob in a
write conditional on it still being `PENDING`. That condition is what makes the three safe to race:
they may arrive together, exactly one of them writes the row, and **only the one that wrote it tells
the host** — so a listener fires once per blob however many paths reach it. A blob already usable is
answered from what is stored and notifies nobody. `onBlobReady` is where thumbnailing, transcoding, virus scanning and every other "we should
proceed file when it uploaded" scenario hangs, and it is after the commit for the same reason
`SyncCommitListener` is — a failure to make a thumbnail must not undo an upload the storage has
already accepted.

**Reaching `READY` is also what the scope's sockets are told.** The module hands the host a
`blobReady` notification exactly as it hands it `onCommitted`, and the host fans it out the way it
already fans out invalidations. It is what turns a deferred attachment from "the other devices will
notice on their next backoff" into "the other devices notice now", and a host that does not publish
it loses seconds to minutes rather than correctness.

**If the processing result has to reach the clients, it travels as a document.** The host writes its
derivative as a *new* blob (blobs are immutable — the original must not be overwritten), registers
it, and pushes an update of the referencing entity through `SyncService.push` under its own
`clientId`. That path already exists and needs nothing new: a server-side push is an ordinary push.

### 7.4 References and garbage

The applier gains one step, inside the transaction that writes the batch and under the counter lock:

```
read what the affected entities currently reference       — before deleting, or it is unknowable
replace sync.blob_refs for every entity the batch wrote with a declared set
clear them outright for every entity the batch deleted
for every blob touched, in two set-based statements:
    gained its first reference → unreferenced_since = null
    lost its last reference    → unreferenced_since = now
```

Both statements are conditional on the value they change, so a blob that merely stayed referenced
keeps the moment it was registered instead of having it rewritten by every unrelated write. The
statement count is bounded by the number of distinct entity **types** in a group rather than by its
operations, which matters because all of it runs while every other writer of the collection waits.

The references of an entity are read **before** they are deleted: a blob that loses its last one is
exactly the blob nothing will mention again, and after the delete there is nothing left to say it
was ever referenced.

A delete clears the entity's references outright. A newly registered blob starts with
`unreferenced_since = created_at`, so an upload whose document was never pushed is garbage from the
moment it was abandoned rather than immortal.

A reference to a blob that is registered and still uploading is recorded like any other. That is
what makes `DEFERRED` safe at this end: the blob is referenced from the moment the record is pushed,
so the sweep cannot take it while its document is already naming it on every device.

What the group is refused for, before any of that, is a reference to a blob this collection has
never registered or has already collected — `BLOB_MISSING`. A correct client does not produce the
first case, because it registers before it names; the second it answers by putting those files back
to where an unregistered file starts, so they are registered and sent again, and letting the group
follow them once they have landed. It is not an ordering check; it is the
check that a reference points at something that exists at all, and it is worth having on the server
because a second implementation of the client, or a bug in this one, would otherwise publish a
reference nothing can ever satisfy.

**That check is taken under the counter lock, which constrains the collector.** It is one indexed
read of at most a row per distinct blob in the group, and it has to be inside the lock rather than
before it: the sweep that could remove a blob must take the same lock, or a blob verified as present
could be collected between the check and the insert — and the reference would then fail on its
foreign key, turning a clean refusal into a failed request. The sweep honours this.

A document may also name more blobs than `maxBlobsPerEntity` allows, which is refused as `TOO_LARGE`
alongside an oversized group or document: the reference list is one more thing a client controls the
length of.

**The rows go first, and the objects are handed over afterwards.** Maintenance finds blobs whose
`unreferenced_since` is older than the retention window, drops their rows under the collection's
counter lock, and only then calls `BlobStorage.onReleased` — outside the transaction, like every
call into the host.

The order cannot be reversed: between choosing a candidate and disposing of its object, a push could
arrive that references it, and an object deleted under a live document is a broken attachment on
every device, permanently. Dropping the row first closes that — from the commit onwards a push
naming the blob is refused `BLOB_MISSING`, which the client answers by uploading again.

What becomes of the object after that is not the module's business and it does not ask. There is
therefore nothing here about objects the storage "refused" to delete, because refusing is a policy
rather than a failure: a host with a legal hold is behaving correctly, and a module that graded the
outcome would be calling that a fault on every sweep, forever.

**A dry run reaches neither the rows nor the host.** It reports the candidates and touches nothing,
which is what to run first on a collection whose clients are not all known to declare their
references.

The window is the same number as everything else, for the third time and the same reason: a client
whose cursor is inside the window may still apply a batch in which the blob was referenced, and one
whose cursor is outside it bootstraps and sees only the current state. Anything shorter is a
`404` on a photograph that should have been there.

A safety rule that is worth stating because it cannot be enforced: garbage collection is per
collection and off by default, and turning it on is a statement that every client writing to that
collection sends `blobs`. A client that predates this extension sends `null`, which the module
respects — but an application that *has* blob support and forgets to answer `blobs()` for one entity
type sends `[]`, and that is indistinguishable from the truth. The sweep's dry run, which reports
what it would delete without deleting it, exists for that afternoon.

### 7.5 Purge

`purgeCollection` and `purgeScope` erase a collection's history and start a new epoch. A purge that
left the photographs in the bucket would not be an erasure, and the one reason an administrator runs
one is that it has to be.

So a purge deletes the blob and reference rows with everything else — the `on delete cascade` above
is not incidental — reads the collection's blobs before erasing them, and hands every one of their
keys to `BlobStorage.onReleased` once the erasure is durable. `PurgeReport` gains `blobs`: how many
files the collection was carrying, and therefore how many keys the host was given.

It does **not** report how many objects were deleted, and for an erasure that matters more than
anywhere else. "The module asked its storage adapter and the adapter returned a list" is a weak
claim; the host's own storage log is both where the deletion actually happens and the only evidence
of it an auditor would accept. The module's part is to make sure the host is told, in full, about
every file the erased collection held — including the ones no document ever referenced, which a
handover driven by references would miss.

**This is the one place the module deletes without waiting for the retention window**, and the
justification is the same one that lets a purge break every cursor in the collection: it is an
answer to an erasure request, and an erasure that waits thirty days is not one.

**The third path to `READY` lives here too.** `confirmPendingUploads` takes every blob still
`PENDING` past its ticket's life and puts it through `markUploaded` — the same call the device and
the storage notification use. A device that wrote its object and died before saying so is otherwise
left with bytes sitting in the bucket that no document can ever fetch. An upload that never arrived
throws from that call, which is the expected and common case: it stays unusable and is collected
later like any other file nothing points at.

On the client the answer is already written and needs one line more. A collection reset (`409`) wipes
the cursor, the records, the groups, the conflicts and the unsent changes; it now wipes the blob and
reference rows too, and calls `BlobStore.remove` for each — not as eviction, but for the same reason
the rest goes: what it belonged to no longer exists.

## 8. The scenarios

### 8.1 A wallet created with a photograph

The photograph is `DEFERRED`, which is the default and the right answer here: a wallet with a name
and a currency is a useful wallet.

```
app     BlobStore.write(B1, bytes)                        — the application's own store
app     collection.mutate { markUpserted(WALLET, w1) }    — the document names B1
lib     push.prepare: snapshot(w1) → doc
                      adapter.blobs(w1, doc) → { BlobRef(B1) }      — deferred
                      sync_blob_ref += (w1, B1, DEFERRED);  sync_blob += (B1, LOCAL)
                      nothing REQUIRED is missing → the group goes out now
lib     push: {op: upsert, entity: wallet, id: w1, data: {…}, blobs: ["B1"]}
srv     B1 is registered → apply, blob_refs += (w1, B1), unreferenced_since = null
blob    POST …/blobs {B1, image/jpeg, 2418123}      → ticket          → UPLOADING
blob    PUT  <presigned>                            → the host's bucket
blob    POST …/blobs/B1/complete                    → verify → READY  → UPLOADED
srv     BlobListener.onBlobReady(B1)  → the host starts its thumbnail
srv     blobReady(ledger, B1) → the scope's sockets
```

The wallet is on the other devices before the photograph has finished leaving this one. B1 must be
registered before the push that names it — that is the one ordering rule `DEFERRED` keeps, and it is
a round trip, not a transfer.

On the second device:

```
lib     pull applies the batch; adapter.blobs(w1, doc) → { BlobRef(B1) }
                      sync_blob_ref += (w1, B1);  sync_blob += (B1, REMOTE)
                      cursor advances — the download blocks nothing
ui      blob(B1) → REMOTE: the wallet renders, the photograph as a placeholder
blob    GET …/blobs/B1 → state: pending, no ticket → backoff
ws      blobReady(ledger, B1) → retry now
blob    GET …/blobs/B1 → ticket;  GET <presigned>  → BlobStore.write(B1, …)  → READY
ui      blob(B1) → READY: the photograph renders
```

### 8.2 A transaction whose receipt never uploads

The case that decides the default. The money is recorded; the photograph is not.

```
app     BlobStore.write(B9, bytes);  mutate { markUpserted(TRANSACTION, t1) }
lib     refs = { BlobRef(B9) }, deferred → the transaction goes out immediately
srv     the movement of money is on every device, seconds later
blob    register, PUT … the file was on an SD card that is no longer there
blob    read(B9) throws → attempts exhausted → UNAVAILABLE
app     BlobStore.onFailed(B9, …) → the application shows a broken attachment and offers a retry
app     the user gives up: mutate { markUpserted(TRANSACTION, t1) } with no receiptBlobId
lib     refs = { } → the field disappears from every device; B9 becomes garbage
```

Nothing was blocked, nothing was lost, and the repair is an ordinary document change. Under
`REQUIRED` the same sequence would have held the transaction — and every group queued behind it —
until the user answered, which is why `REQUIRED` is for a record whose file is its content and not
for a receipt.

### 8.3 The photograph is removed

```
app     collection.mutate { markUpserted(WALLET, w1) }    — the document no longer names B1
lib     adapter.blobs(w1, doc) → { }
                      sync_blob_ref -= (w1, B1)
                      B1 is referenced by nothing → BlobStore.remove(B1)   — an offer
lib     push: {…, blobs: []}                              — explicit, not null
srv     blob_refs -= (w1, B1);  B1.unreferenced_since = now
…       30 days later: maintenance → rows dropped → BlobStorage.onReleased([B1]) → the host's
```

### 8.4 The photograph is replaced

8.1 and 8.3 in one transaction, and under `DEFERRED` there is no ordering to get right at all: the
document naming B2 goes out at once, B2 uploads behind it, B1 leaves as above. On every other device
the pull applies the new document, references {B2}, enqueues the download and offers `remove(B1)` —
none of which needed a new mechanism, because replacing a photograph is, to this design, an ordinary
document change that happens to move a reference.

### 8.5 A photograph nobody opens

The receiving device, configured `blobFetch = ON_DEMAND`:

```
lib     pull applies the wallet naming B1, advances the cursor
lib     adapter.blobs(w1, doc) → { BlobRef(B1) }          — no policy stated: the engine's applies
                      sync_blob_ref += (w1, B1, fetch = ON_DEMAND)
lib     reconcile: bytes absent → sync_blob(B1, REMOTE, wanted = 0)
lib     nothing is queued; no request is made; blobReady for B1 finds nothing to do
app     the wallet list draws a placeholder and an offer, from BlobSyncState(REMOTE, wanted = false)

… the user opens the wallet:
app     collection.fetch(B1)
lib     sync_blob(B1).wanted = 1  → the worker wakes
lib     GET …/blobs/B1 → ticket → bytes → BlobStore.write/finish → READY
app     the same flow now says READY, and every later opening of that wallet draws the file

… the user, or the application's own housekeeping, wants the space back:
app     collection.evict(B1)
lib     BlobStore.remove(B1), then sync_blob(B1) → REMOTE, wanted = 0
```

Nothing in that sequence touched the log, the cursor, the queue or the server's view of anything.
The document said the same thing throughout, the reference row existed throughout, and the only
thing that changed is one bit on one device — which is the whole of what this policy is.

## 9. How it fails

| What happened | What the library does |
| --- | --- |
| The local file is gone before the upload, `DEFERRED` | `UNAVAILABLE` and `BlobStore.onFailed`. The record is already on the server and nothing is blocked; the application shows a broken attachment and the user decides whether to retry or drop the field |
| The local file is gone before the upload, `REQUIRED` | The same, plus `adapter.onRejected(entityType, id, BlobUnavailable)`: the group is `FAILED` and the queue stops on it, exactly as for an oversized group. Only the application can move it — drop the reference, or attach another file |
| The upload ticket expired mid-transfer | Register again, upload again. The blob row is the state; nothing is lost but the bytes already sent |
| `complete` says the host cannot find the object | Back to `LOCAL` and upload again, bounded by attempts, then `UNAVAILABLE` |
| The device died between `PUT` and `complete` | The host's storage event (7.3 path 2) or the sweep (path 3) promotes the blob; the client's `complete` on the next run is a no-op |
| The push is refused `BLOB_MISSING` | The blob was collected while the group sat blocked, or was never registered. It goes back to `LOCAL`, is registered and uploaded again, and the group is re-sent under a **new** identifier — its content is unchanged, but the server stored an answer under the old key |
| The download says `pending` | The blob is registered and still uploading — the ordinary state of a deferred attachment that arrived ahead of its bytes. Retried on a capped backoff, and at once on `blobReady` |
| The download is a `404` | The blob was collected while this device was away, or its collection was purged. `UNAVAILABLE`, `BlobStore.onFailed`. Not a collection failure: the next pull usually supersedes the reference, and a purge announces itself on the next sync call anyway |
| The download's bytes disagree about size or checksum | Discarded and retried; a truncated file written into the application's store would be worse than none |
| A file nobody asked for is never fetched | Nothing, on purpose. It is not a failure, it is not retried and it is not counted as incoming; it sits `REMOTE` and unwanted, and the application's own screen is what turns it into a request |
| A file asked for that no document names | The request is refused with a line in the log. Reconciliation would offer the bytes straight back, so honouring it would be fetching a file to delete it |
| A file asked to be given up whose bytes are the only copy | Refused with a line in the log, and the bytes stay. Only `UPLOADED` and `READY` say the server has them too |
| The blob limit is exceeded | Refused locally, before registration, like an oversized group: `onRejected(entityType, id, TooLarge)` |
| The server serves no blobs | The engine refuses to start with a `BlobStore` configured, naming the collection. Better at start-up than as a `404` on the first photograph |

`SyncRejection` gains one case, `BlobUnavailable`. It is a sealed class, so that is a source-breaking
change for an application with an exhaustive `when` over it — deliberate, and the reason it is worth
the break is that a silently-absorbed blob failure is a queue blocked with no explanation.

## 10. What is unchanged, and therefore worth stating

- **The change log.** No new operation code, no `blob` entry, no new field on `RemoteOperation` or
  `SnapshotItem`. Adding an operation code is a breaking protocol change, as §8 of the server
  specification says; this extension does not need one, because a reference is part of the document
  and the document already travels.
- **The event channel, in kind.** `blobReady` is one more alarm clock on a channel that already
  carries three, and it is compatible by construction: §9 of the client specification defines an
  unknown event as a generic invalidation, so a client that predates it answers with one extra pull
  and stays correct. It carries no data, like the rest of them.
- **The cursor, the epoch, versions, ordering, the counter lock.** A blob has none of them. No
  invariant in §5 of the server specification is touched.
- **Conflicts.** Entirely unchanged. `TakeServer` on a wallet whose photograph differs moves the
  reference, which enqueues one download and offers one removal, and every bit of that falls out of
  the reconciliation in 6.3 with no conflict machinery involved.
- **Bootstrap.** A snapshot carries documents; references are recomputed per item; missing bytes go
  into the download queue and the collection reaches `LIVE` without waiting for a single one of
  them. The sweep removes reference rows with the entity rows, by `seen_gen`.
- **Echo suppression, the inbox, two-phase pull.** A blob is not in a batch and cannot echo.
- **`SyncLog` and `SyncMetrics` rules.** New events on both sides; the standing rule that no record
  carries a document extends to say that **no record carries a ticket URL** — it is a bearer
  credential, and a debug log is pasted into bug reports. Records carry the blob identifier, its
  size and its state.

## 11. What is deliberately not built

**Resumable and multipart uploads.** One `PUT` per blob. A 4 GB video over a train's connection
wants range resumption, and S3's multipart means N presigned URLs and a completion call — a stateful
upload session, garbage collection of abandoned parts, and a new failure surface, which is the same
trade §7 of the server specification already declined for oversized groups. The ticket's shape,
`{method, url, headers, expiresAt}`, is what leaves room: a host can presign its own resumable
endpoint today without either SDK knowing, and the protocol-level version is the recorded fallback
for the day a real workload produces a blob the single `PUT` cannot carry.

**Transcoding, thumbnails, or any knowledge of what the bytes are.** The module stores a content
type it was told and never reads it. A thumbnail is a second blob the host makes in `onBlobReady`.

**Filtering what a collection's files *are*** — a device that is sent the thumbnails and never told
the originals exist. That is the subscription-filtering question of §8 of the server specification
wearing different clothes, and the answer is the same: the shape that works is two blobs and a
document that names both, so every device agrees about what exists and the library transports what
it is told.

What *is* built, and is a different question, is which of the files it knows about a device holds:
the fetch policy of §4. The distinction is worth keeping sharp. The policy never hides a file — the
reference is on every device, the row exists, the state is published — it only declines to spend
bytes on one until something asks. A filter would mean two devices disagreeing about what a document
points at, which is the thing this design will not do.

**Encryption.** As for documents: the host sees plaintext. An application that needs otherwise
encrypts before `BlobStore.write` and decrypts after `read`, and the library is none the wiser —
which is the one place this design is genuinely easy to extend, because it never looks at a byte.

## 12. What each side must provide

**The host**, in addition to §15 of the server specification:

1. Implement `BlobStorage` over its object storage — four methods, presigning and a `HEAD`.
2. Publish the three endpoints on top of `SyncBlobService`.
3. Keep tickets short-lived, and scope them to the single object.
4. Call `markUploaded` from its storage's event notifications, if it has them. It should.
5. Do whatever it does in `onBlobReady`, and never overwrite the object it was given.
6. Publish `blobReady` to the scope's sockets, beside the invalidations it already fans out.
7. Run the blob sweep on a schedule, and read its dry run before switching deletion on.
8. Dispose of what `BlobStorage.onReleased` hands over, and record having done so. That record is
   the erasure's evidence — the module keeps none, because it has no way to observe the outcome and
   a second-hand account of a deletion is not one an auditor would take.

**The application**, in addition to what the client specification asks:

1. Answer `CollectionAdapter.blobs(...)` for every entity type that can reference one — the whole
   set, every time, because the answer replaces what is stored.
2. Decide the binding of each reference, which is the first of the two editorial decisions here: is
   this record worth publishing without its file? For a receipt, an avatar or a photograph of a
   wallet the answer is yes, and `DEFERRED` is already the default. Reach for `REQUIRED` only when
   the record without its file would mislead somebody.
3. Decide the fetch policy, which is the second: is this file worth holding on a device before
   anybody asks for it? `EAGER` is the default and is right for anything a list draws. For the
   large ones, set `blobFetch = ON_DEMAND` on the engine or on the reference, and call
   `CollectionHandle.fetch(blobId)` from the screen that opens the record — and keep the file's size
   and media type in the document, because a file that has never been fetched has never been
   described.
4. Implement `BlobStore` over its own file storage, and write the bytes **before** the `mutate` that
   references them.
5. Render `REMOTE` and `DOWNLOADING` as states the user sees, because they are not errors — and, if
   it fetches on demand, render `REMOTE` with `wanted = false` as an offer rather than as a wait.
6. Handle `BlobStore.onFailed`: under `DEFERRED` it is the only notice that an attachment will never
   arrive, and the record it belongs to is already published.
7. Decide, in `remove`, whether it keeps a file nothing references — and decide for itself when to
   `evict` one it fetched, because the library imposes no ceiling on somebody else's storage.
8. Handle `BlobUnavailable` in `onRejected`, if it uses `REQUIRED`: it is the one blob failure that
   blocks the queue and only the application can clear.

### 12.1 What the host can read back

`SyncQueries` grows `blob` and `blobs`, paged by identifier. It is the only view of what no client
can see: the key the storage chose, a file registered but never sent, and how long something has been
waiting out the retention window before the collector offers it back. From a device a file is either
there or it is not.

The page token here is the last identifier and nothing else. A snapshot's token also carries a
cursor, because every page of one snapshot has to describe the same moment; this read makes no such
promise — it is an administrative view of a table that is still being written — so the position is
the whole of it.

## 13. Where the tests are

The mechanism here has three seams that nothing above them can check, and each has a suite of its
own rather than being covered incidentally.

`server-sdk` tests the module against real PostgreSQL and a fake bucket: the schema and its cascades
(`BlobSchemaTest`), registration, verification and the once-per-file acknowledgement
(`BlobServiceTest`), reference bookkeeping inside the counter lock (`BlobReferenceTest`), and the
collector, the promotion sweep and purge (`BlobMaintenanceTest`).

`client-sdk` tests the two halves that are invisible from outside: the queries that decide what is
work (`SyncBlobDaoTest`), reconciliation, which produces only rows (`BlobReconciliationTest`), and
the worker, most of whose tests are about failing rather than succeeding (`BlobWorkerTest`). One
test in `KtorBlobTransportTest` exists for a single assertion — that a presigned request carries
none of this library's credentials.

`samples/ledger-server` carries `PhotoSyncTest`, where every piece is the real one: PostgreSQL, the
module, HTTP, presigned URLs, and two devices with separate file stores on disk. It is the only
place the whole path is exercised at once, and it is what found the ordering rule in §4 — a record
was being published naming a file the server had never been told about, and the server refused the
whole group for it.
